## 那个「突然拉到底」是怎么来的

`shock` **不是随机数**。它的触发条件是**真实观测到的剧烈变化** —— 某一根 15 分钟里
CAPE 炸了、阵风猛增、或者开始下暴雨，`sev` 就会跳一大截，超出的部分变成一记冲击。
系数是拿广州 / 哈尔滨 92 天的真数据调的，调完之后：

| | 基线（没有冲击） | 现在 |
| --- | --- | --- |
| 单根涨跌 中位 | 0.169% | **0.190%**（平时盘感基本没变） |
| 单根涨跌 p99 | 3.06% | **6.28%** |
| 连续 3 根最大跌幅 中位 | 4.4% | **7.3%** |
| 连续 3 根最大跌幅 p90 / 最大 | 4.9% / 5.9% | **8.2% / 9.7%** |
| 出现过 3 根跌 ≥8% 的局面 | — | **14 / 60 局** |

`shock` 是「这一刻打多狠」，`carry` 是「余波还走多远」。只有 `shock` 的话就出一根长阴、
下一根立刻回弹，不像崩盘；加上 `carry`（按 0.78 衰减的动量）才有连续几根顺势砸下去的样子 ——
这就是《FX 战士久留美》第一话开头那种「蜡烛图突然拉到底」。

**所以没有真实天气过程的时候，盘面就是平静的。** 平静的时候你赚不到钱，
也正是这种时候最容易上杠杆，然后被一次对流爆发带走。

## 系数是调出来的，不是拍的

`50 / 16` 这两个数拿真数据（广州 / 哈尔滨各 92 天）试出来的，目标是让行情「走得动、但不变成随机数」：

| 指标 | 实测（广州） |
| --- | --- |
| 单根 15 分钟涨跌 | 中位 **0.19%**、p99 **6.3%**、最大 **10.6%** |
| 单日振幅 | 中位 **12.7%**（五天分别是 5.2% / 9.5% / 18.2% / 12.7% / 15.0%） |
| 指数区间 | 937 ~ 1110（基准 1000） |

对比过几组：`A=30,B=10` 只有日均振幅 5.5%，`A=40,B=15` 到 7.7%；
而单纯加大噪声（`scale=40, EMA a=0.5`）能到 12.3%，但曲线是**纯噪声、没有趋势可骑**。
`50/16` 是两头都占住的那组。

突发行情那一组也对比过四档：`AT=1.2 K=22` 太温和（3 根跌最大只有 8%），
`AT=0.8 K=30` 太频繁（每局 5.7 次单根 >6%，盘面变成噪声），
最后取 **`AT=0.9 K=34 decay=0.78`** —— 中位不变、极端值够狠、每局大约出现一次。

**一个测试指标上的坑**：一开始我用「单日振幅」和「10 根窗口内最大行程」衡量刺激程度，
加完冲击发现几乎没变 —— 因为这两个指标都被趋势主导了。真正区分「突然拉到底」的是
**连续 3 根 / 5 根的最大跌幅**，换成这个指标差异立刻就出来了。测错了指标会得出「改了没用」的错误结论。

## 几个实现上的选择

- **界面不显示真实日期**，只显示「第 3 天 14:15」。否则去翻历史天气就知道后面怎么走，
  这局就没得玩了 —— 取样窗口是随机的，连开两局不会是同一段。
- **它是铺满整个视口的，不是一个居中对话框**。最初写成
  `width: min(1180px,100%)` 的居中面板，在 1600 宽的屏上四周会露出一圈主站 ——
  用户看到的观感是「怎么只有屏幕中间那块变成 K 线了，主站的曲线还在」。
  改成 `inset:0` + `width/height:100%` 之后主站一点都看不见，才像个正经交易终端。
- **顶上有条 MT4/MT5 那样的行情条**（品种 / 15M / 买卖价 / 点差 / 行情时间 / 连接状态），
  右侧价格轴上贴着**现价标签**，大号下单键上直接印着现价 —— 这几个都是真交易终端看惯了的东西，
  少了就觉得"不像"。其中「点差」显示的是**真实成本**（一手开+平两次手续费折算成指数点），不是摆设数字。
- **下单前先让你看清这一单有多大**：名义仓位 / 开仓手续费 / **约可承受反向波动 X%** 三行，
  下面还有「成交记录」。这三行是照 bilibili 那个「FX 简单!」的下单卡搬的 ——
  它把「杠杆」和「仓位」两件事合成了一个数字交给你，比只显示一个「30%」有用得多：

  | 杠杆 | 10% 仓 | 30% 仓 | 50% 仓 | 满仓 |
  | --- | --- | --- | --- | --- |
  | 1× | 993% | 324% | 191% | 90.4% |
  | 10× | 99.4% | 32.5% | 19.1% | 9.03% |
  | 20× | 49.7% | 16.2% | 9.53% | 4.52% |
  | 100× | 9.93% | 3.24% | 1.90% | **0.90%** |

  推导：开仓后现金 `C`、保证金 `M = 手数·价·LOT÷N`，爆仓时 `C + 手数·Δp·LOT = M·10%`，
  所以 `Δp = (M·10% − C) ÷ (手数·LOT)`。满仓时它化简成 `(1−10%) ÷ N`，
  和上面那张表最后一行对得上（20× 实测 4.517%，理论 4.500% —— 差的那点来自手数向下取整）。
- **行情是"滚动揭示"的**：主图只画 `G.i` 之前的 K 线，跟真行情一样右端在走。
  而且**只画最近一屏**（`visBars()` 按容器宽 ÷ 9px 算，跟真实操盘软件一样自动滑动）——
  960 根全塞进 1300px 的话一根才 1.3px，蜡烛会糊成一条线。
- **两根均线 + 十字光标读数**：MA5 / MA20，鼠标在图上来回划时左上角那行
  `开 高 低 收 + MA5 + MA20` 跟着走（TradingView / MT4 的图例就是这样）。
  均线要**拿整段 `series` 算完再切可视段** —— 只拿可视段算的话，每次窗口滑动
  均线都会整体跳一下，看着像在抽搐。
- **上下影线是建模的，不是实测的**。15 分钟粒度拿不到根内的真实最高最低：
  开盘价 = 上一根收盘、收盘价 = 本根指数（这两个都是真采样），
  影线按 `|本根涨跌| × 0.30` 补出来。这条别说成"全真数据"。
- **天气闪报**：雷暴 / CAPE ≥ 3000 / 阵风 ≥ 25 / 短时强降水 / 天气转好时会从顶上滑下一条横幅，
  数值都是当根 K 线的真值（`newsAt(i)`）。同一个事件不重复播。
- 音效是 WebAudio **现场合成**的（`beep(freq, dur, type, vol)`），不引任何音频文件；
  爆仓时另外 `navigator.vibrate([80,60,220])`。
- 键盘 `↑`/`W` 做多、`↓`/`S` 做空、`空格` 平仓。
- 权益曲线画的是**账户权益**（`现金 + 浮动盈亏`）而不是余额，所以持仓期间它跟着价格跳。

## 一个数据源上的坑

Open-Meteo 的 `minutely_15` **两个主机的历史深度不一样**：

| 主机 | `past_days=92` 的结果 |
| --- | --- |
| `historical-forecast-api.open-meteo.com` | **8928 个点全部非空**（2026-07-06 → 10-06） |
| `api.open-meteo.com` | 同样 8928 个点，但**只有 6692 个非空**，更早的全是 `null` |

**只看 HTTP 状态码发现不了这件事 —— 它照样返回 200 加一串 null。**
所以 `OpenMeteo.minutely()` 先试 historical 主机，并抽查最早一天的非空比例，
低于 50% 就换主机。

## 为什么需要"三级取数"

`d1.weather.com.cn` 会**强制校验 `Referer` 必须是 `weather.com.cn`**，浏览器里补不了这个头；
`weather.cma.cn` 又会在非浏览器 UA 下返回 `406`。所以前端按下面的顺序依次尝试，谁通用谁：

```
① 本地代理（APK 自带 / 本地调试用）  →  服务端补 Referer / UA，最稳
② 浏览器直连                  →  网页版走这条；weather.cma.cn 有 CORS 头，d1 拿不到
③ 静态兜底 data/official/**   →  GitHub Actions 每 30 分钟预抓并提交的 JSON
```

网页版因此是 ② + ③：能直连的就直连，拿不到（比如 d1 的官方预报）就读仓库里 Actions 刚抓好的快照。

## Open-Meteo 的免费额度，以及为此做的节流

Open-Meteo 免费档（非商业）的硬上限是**每分钟 600 次 / 每小时 5,000 次 / 每天 10,000 次**，
**超了不会提前通知，直接封 IP**。被限流时接口返回的就是这一句：

```json
{"error":true,"reason":"Daily API request limit exceeded. Please try again tomorrow."}
```

本站绝大多数请求走的是中国天气网（`Cma.now`，无论多少城市都只读一份快照），
真正会随「城市数 × 时间」放大的是 Open-Meteo。实测方式：`?local=0` 把页面挂 2 小时
（用 `--virtual-time-budget` 压缩应用时间），从 iframe 的 Resource Timing 里数请求。
最初的构成是：

| 调用 | 次数 / 2 小时 | 说明 |
| --- | --- | --- |
| `current=` 实况兜底 | **720** | 无官方站号的城市（典型是「当前所在地」）用 Open-Meteo 当前值当报价 |
| `brief` 昨收 / 迷你走势 | 68 | 自选 + 热门，每个坐标 4 次 = 2 小时里 4 轮 |
| `past_days=92` 历史逐时 | 12 | 画日 K 用的 92 天历史 |
| `archive` / `air-quality` | 4 / 4 | 归档与空气质量 |

折合约 **9,650 次/天**，正卡在免费额度上。根因不是"请求太多"，而是
**缓存只在请求成功返回之后才写入** —— 只要一次请求还没落地（网络慢，或者上游 20 秒
的超时比 10 秒的轮询间隔还长），下一个 tick 就再发一次，于是永远存不上，退化成
「每个轮询 tick 一次」。

修法在 `web/js/api.js` 的 `getJSON()`：

- **`inflight` 表**：同一个 cache key 正在飞的请求只保留一个 Promise，后来者直接复用
- **失败也缓存**（`FAIL_TTL = 60000`）：上游 429 / 超时之后 60 秒内不再重试
- `warmQuotes()` 里 `BRIEF_MS = 1800000`（30 分钟一轮）、`BRIEF_MAX = 40`（一轮最多 40 城）；
  注意 **brief 的 TTL 必须写成和节流周期同一个值**，否则缓存先过期，节流等于没做
- 轮询间隔默认从 3 秒改成 **10 秒**（`web/index.html` 的下拉里仍可选 3 秒）

改完复测同样 2 小时：**总请求 804 → 183，其中 `current=` 720 → 103**，折合约 2,200 次/天。

轮询间隔默认设成 **15 分钟**（下拉里仍可选 1 秒 ~ 5 分钟）。因为额度是**按 IP 计**的，
被限流时接口返回的就是上面那句 429 —— 而且**只影响被限流的那台机器**，
换一台设备、换一个网络出口，额度就是全新的一份。所以调试时千万别用
`--virtual-time-budget` 长时间跑页面，那会把真实当天的额度一次性烧光。

## 额度用光时的退路：换一台 Open-Meteo 主机

免费额度是**按主机名分桶**的，这一点不看文档看不出来 —— 实测把
`api.open-meteo.com` 打到 429 之后：

| 主机 | 当时状态 |
|---|---|
| `api.open-meteo.com`（forecast） | **429** `Daily API request limit exceeded` |
| `archive-api.open-meteo.com`（archive） | 200 |
| `air-quality-api.open-meteo.com` | 200 |
| `historical-forecast-api.open-meteo.com` | **200** |

而 `historical-forecast-api.open-meteo.com/v1/forecast` 的**参数和返回结构跟主站完全一致**，
连 `past_days` + `forecast_days` 那一段未来预报都照给（实测
`past_days=92&forecast_days=16` 返回 `2026-07-06..2026-10-21`，与主站等价）。所以它就是
一个免费的备份源。三处都加了主机回退，谁行用谁，并把可用的那台记下来（`omHost`），
下次先走它，不必每次都去撞墙：

- `web/js/api.js` 的 `omGetJSON(q, opt)` —— `brief` / `forecast` / `mini` / 实况回退都走它
- `web/js/weather.js` 的 `jgetOm(q, ttl, key)` —— 逐小时那一个大请求走它
- `server/app.py` 的 `om_passthrough()` —— 本地代理 / APK 那条路也照样回退

缓存 key 末尾带 `#h<idx>`（两台主机各存各的），否则一台的失败记录会把另一台也堵住。

写这段的起因值得记一笔：**429 期间页面的表现极具误导性**。中国气象局的数据全都正常
（气温、湿度、风、气压、日 K 全部有值），只有 Open-Meteo 来的字段变成 `--`：
自选/热门列表整列涨跌幅、平均风速、日出日落、5 天落差。看上去像"功能坏了"，
实际上是二级源被限流、一级源好好的 —— 而主图和副图的横轴对齐、K 线形态这些
"看起来最像坏掉"的部分反而完全正常。

还有一个我自己埋的坑：`warmQuotes()` 里原本不管成败都写 `S.briefAt = Date.now()`，
于是一次失败（比如当天额度用光）就把整列涨跌幅**锁死半小时**，期间一次重试都没有，
额度恢复了也不会自己好。现在 `S.briefAt` 是"下次允许拉的时刻"：成功推 30 分钟，
**失败只推 2 分钟**，能自己恢复。

一个曾经踩过的坑：`OpenMeteo.archive()` 的缓存键漏了 `endDate`
（原来是 `'a|' + lat + ',' + lon + '|' + startDate`）。同一 start、不同 end 的两次调用
会互相命中缓存，第二次等于没发出去。目前只有一个调用点所以没暴露，但键该带上就带上。

## 再退一步：「昨收」改用气象局日历算

主机回退解决的是"某一台被限流"。要是两台都不通（断网，或者两家额度一起见底），
自选/热门列表那整列涨跌幅还是会全 `--`。所以昨收又加了一层**完全不依赖 Open-Meteo** 的兜底：

- `web/js/api.js` 的 `Cn.brief(city)` —— 读中国天气网的**月度日历**（就是日K页用的那套
  `calendar_new`），把**昨天**那天的**实测日均温** `(maxobs + minobs) / 2` 当作昨收，
  再用最近几天的日均温拼一条迷你走势。当月文件通常带着上月末尾几天，所以一份就够；
  万一不够（月初抓的当月文件从 1 号起）再补一份上月。
- `web/js/app.js` 的 `briefOf(city, ttl)` —— 先试 `OpenMeteo.brief`，拿不到 `prevClose`
  才走 `Cn.brief`。正常情况下**一次多余的请求都不会发**。

**两个源的「昨收」定义不一样，这是数据粒度决定的，不是 bug：**

| 源 | `prevClose` 的含义 | 粒度 |
|---|---|---|
| `OpenMeteo.brief` | 昨天最后一个整点的气温（真正的"收盘价"） | 逐小时 |
| `Cn.brief` | 昨天实测日均温 `(maxobs + minobs) / 2` | 逐日 |

所以同一个城市在兜底模式下算出来的涨跌幅，**数值会和平时有出入，偶尔连正负号都不同** ——
24 ℃ 的现价，跟"昨天 23 点 20 ℃"比是涨，跟"昨天日均 27.5 ℃"比就是跌。
这个出入可以接受（毕竟整件事就是把天气包装成行情，两边都是从真实观测算出来的），
但**别把两条线上的百分比当成同一个指标来横向比较**。

覆盖范围也是分开的：桌面版 / APK 走本地代理，`d1` 域随便抓，**352 城全都有**；
GitHub Pages 是纯静态站，只有 `tools/prefetch_official.py` 预抓过的城市才有
`data/official/cal/` 文件（当前 45 城，**热门 22 城全在其中**），其余城市在网页版上
拿不到兜底值，仍会显示 `--`。

日历里只有 `cla='obs'` 的日子带 `maxobs/minobs`（更早的是 `cla='history'`，只有历史同期
均值），所以兜底时的迷你走势通常只有**最近 5 天**。线短一点，形状是对的。

## 没有手机怎么测 APK

本机没有 `adb`、也没有连过任何安卓设备，所以"装到手机上"这一步没法自动化。
退一步，**把最容易出错的那部分单独拎出来在 PC 上跑**：APK 里真正容易被改坏的，是
`MainActivity` 里那些把中国天气网的文件解析成 JSON 的 Java 代码（正则、编码、`var` 前缀剥离）。

- `tools\test_apk_parser.py` 直接 `subprocess` 调 `D:\Java\bin\javac` / `java`，把
  `android\test\TjsParseTest.java` 编出来跑，喂进真实的抓取内容，**25 项断言**覆盖：
  `var cityDZ101010100 ={...}` 的 `var` 剥离、GBK 解码、`sk_2d` / `dingzhi` / `calendar_new`
  三种文件形态、`oot` 字段空缺、以及台风 JSONP 的双层括号。
- `android\test\` 只进仓库、**不进 APK**（`build_apk.py` 的 `SKIP_ASSET` / 编译清单都不含它）。

其余部分（WebView 装载、拦截器路由、签名）只能靠真机验证 —— 这一点在下面的
「已知限制」里如实写着。

## 一些实现上的坑（给后来的人）

- **手机窄高屏上 `flex:1` 的图表会塌成 0 高**：`.chart-box{flex:1;min-height:0}` 在高度不够时会被压到 0，
  而隔壁 `.chart-box.sub{flex:0 0 132px}` 有固定 basis 照样可见 —— 表现就是"主图不见了，页签下面直接是副图"。
  窄屏必须给 `.chart-box{flex:1 1 auto;min-height:170px}`，再把整页高度交给 `.pane-center` 内部滚动。
- **底部页签不会自己工作**：`index.html` 里 `<button class="mtab" data-mtab="N">` 只是标记，
  事件要在 `bind()` 里自己挂（`closest('.mtab[data-mtab]')` → `setMTab`）。当初只有 `setMTab`/`syncMTabs`
  和深链分支，四个按钮全是死的 —— 而且不报错，只是点了没反应。
- **ECharts 的 x 轴标签会被自己的 dataZoom 滑块盖住**：`grid(l,r,t,b)` 的 `b` 必须大于
  滑块高度 + 底部间距。`{type:'slider', height:15, bottom:5}` 占 `H-20` 往上，而 `b=34` 时
  标签正好落在 `H-26 .. H-14` —— 两者重叠。主 K 线图现在用 `b=46`。
- **ECharts 的 K 线把"平盘"当阴线**：`candlestick` 判阳线用的是**严格** `close > open`，
  `close === open` 会落进 else 分支、套用跌的 `color0`/`borderColor0`（在仓库自带的
  `echarts.min.js` 上实测确认）。气温 K 线里这种"一天下来没升没降"的日子占 **3.3%**
  （576 天里 19 天），所以凡是在别处自己判涨跌，算子必须跟它对齐 —— 量能柱原来写的是 `>=`，
  于是平盘那天会出现「**上面一根绿 K 线、下面一根红量柱**」。现在平盘统一涂中性灰：
  K 线用 per-item `itemStyle`（数组式和 `{value, itemStyle}` 对象式可以混用，
  `markPoint` 的 `valueDim: 'highest'/'lowest'` 在对象式数据下实测依然生效），
  量柱在 `data[i].itemStyle.color` 上判。
- **别拿摄氏温度当分母算"涨跌幅"**：气温是**间隔尺度**（interval scale）量 —— 零点是人为约定的
  "水的冰点"，不是"没有温度"。比值只在**比率尺度**（有真零点）上才有意义，判据很简单：
  同一件物理事实换个单位结果就变。21.0℃ → 22.5℃ 在摄氏下是 `+7.14%`、开尔文下 `+0.51%`、
  华氏下 `+3.87%`，三个数说的是同一天。股票价格是比率尺度（0 元就是真的没钱），气温不是。
  这不只是"意义可疑"，而是**会直接算错**：
  - **0℃ 以下是负的**，于是分母变号 → **涨跌方向整个反过来**。哈尔滨
    2025-12 ~ 2026-02 的 90 个交易日里，收盘价在 0℃ 以下的有 **88 天（98%）**，
    其中 **47 天**是"升温却显示成负数"；最离谱的 2025-12-23 开 `-4.8`、收 `-16.1`
    （大降温 11.3℃）却显示 **`+235.4%`**，2026-02-22 开 `5.9`、收 `-10.9` 显示 **`-284.7%`**。
  - **0℃ 处除零**（`1.0 / 0.0` → `Infinity`）、接近 0℃ 时爆表（`3.0 / -0.5` → `-700%`）。
  - 即使在零上，量级也不对：`pct_摄氏 / pct_开氏 = (T + 273.15) / T`，20℃ 时相差 **14.7 倍**，
    广州 +1.5℃ 显示 `+7.14%`、武汉 +7.1℃ 显示 `+39.35%` —— 放在炒股壳子里非常违和。

  所以统一改成 `U.pctOf(cur, base) = (cur - base) / (base + 273.15) * 100`，
  凡是"气温 / 气温"的地方全部走它：行情头、指数条、自选列表、K 线 tooltip、分时 tooltip、
  分时右侧百分数轴、以及 BOLL 带宽（`indicators.js` 的 `(上轨-下轨)/中轨`）。
  **KDJ 的 RSV、RSI、WR 不用动** —— 它们的分母是**温差**（`hh - ll`）或涨跌绝对量之和，
  本来就与零点无关。**BOLL 带宽要动**（`(上轨-下轨)/中轨`，中轨是气温均值）：
  中轨为负时带宽会变成**负数**（-10℃ 附近实测 **-144%**、-2℃ 附近 **-787%**、
  +2℃ 附近又翻成 **+641%**），穷举中心 -40~45℃ 的 3526 个取值，改完之后
  非正/非有限值 **0 个**，全部落在 3.6%~5.4%。

  代价要知道：大气温度只在 273~313 K 之间晃，分母几乎是常数，于是比值退化成
  `ΔT × ~0.0034`，基本就是**绝对差的线性重标定**，"相对变化"那层含义没有了。
  但这正是物理上的实话 —— 对气温而言有意义的量就是绝对差 ΔT 本身。
- **月K 的键不是完整日期，别拿它算星期几**：K 线 tooltip 的标题原来是
  `b.d + ' ' + weekday(b.d)`。日K 的 `b.d` 是 `'2026-10-06'`、周K 是那一周的周一（也是完整日期），
  都没问题；但月K 的键只有 `'YYYY-MM'`（`indicators.js` 的 `keyOf` 返回 `d.d.slice(0, 7)`），
  而 `U.parseDate` 是 `new Date(+p[0], +p[1] - 1, +p[2])` —— `p[2]` 是 `undefined`、`+undefined` 是 `NaN`，
  于是 `new Date(2025, 10, NaN)` 得到 **Invalid Date**，`getDay()` 返回 `NaN`，
  最后 `'周' + w[NaN]` 就是 **`周undefined`**（用户看到的就是标题写着 `2025-11 周undefined`）。
  **JS 在这里一声不响**：数组下标是 `NaN` 只返回 `undefined`，拼进字符串就成了给用户看的东西，
  既不报错也没有 `TypeError` 兜底。
  修法是两头都收一下：`U.weekday()` 拼不出星期几时返回**空串**而不是 `'周undefined'`
  （判据是 `d.getDay()` 的 `NaN` 自己不等于自己），tooltip 标题改走一个 `tipTitle(d)` ——
  有星期几就写 `2026-10-06 周二`，只有年月就写 `2025 年 11 月`，别的原样输出。
  同一族的问题还有一处：周K / 月K 是**聚合**出来的，`indicators.js` 只带了
  `{d,o,h,l,c,v,n,raw}`，没有 `range` / `windAvg` / `humAvg`，于是量能那一行固定显示
  `日内温差 -- ℃`（月K 下副图本来就是隐藏的）。现在取不到就**整行不显示**，
  而不是画一行占位的破折号 —— 日K 那行不受影响（实测 553 根全有值）。
- **气象局的"没有观测"是 `9999`，不是 `null`**：`weather.cma.cn` 对没有实时观测的站，
  会把**每一个**字段都填成哨兵 —— 数值字段给 `9999`、字符串字段给 `"9999"`、
  `lastUpdate` 停在最后一次正常上报的时刻（不是空、不是 0、更不是当前时间）。
  实测澳门（`45011B`）的 `lastUpdate` 是 **2025/08/08 10:25**（一年前）、
  台北（`58968`）是 **2025/04/23 21:17**，`data.now` 里 9 个字段全 9999；
  而同一时刻广州（`59287`）的 `lastUpdate` 是 `2026/10/06 10:00`，字段全是真值。
  最容易漏掉的是它**不只出现在港澳台**：Actions 预抓的 40 份静态 `data/official/cma/*.now.json`
  里有 **6 份**带 9999 —— 除澳门/台北外还有 **上海（`58367`）/ 郑州（`57083`）/
  株洲（`57780`）/ 成都（`S1003`）**（成都的站号甚至是非数字的），
  而这几个站**打实时接口会返回正常值** —— 说明 9999 是**偶发**的。
  所以过滤必须**按值判**，不能按城市白名单，也不能只靠"这个站是不是港澳台"。
  `web/js/api.js` 的 `Cma.now()` 原来把上游字段原样透传，于是哨兵变成了"真温度"：
  - `Store.quote()` 里写的是 `if (n && n.temp != null) return n;` —— `9999.0 != null` 成立，
    于是哨兵被收下，而且**永远走不到下面的 Open-Meteo 兜底**；
  - 详情头 `quoteOf()` 又**优先**取 `S.quotes[id].temp` 而不是中国天气网快照，
    于是表现成「**搜索时看着正常、一加入自选就炸**」：加入自选后列表轮询把 `q.temp = 9999`
    填了进去，涨幅变成 `9999 - 23.9 = 9975.1`、`9975.1 / (23.9 + 273.15) ≈ +3358%`，
    湿度 `9999%`、风速 `9999 m/s`、气压 `9999 hPa`、体感 `9999.0℃`、风向 `9999` 一起炸，
    9999 还会在自选按涨幅排序时顶到最上面。
  现在 `Cma.now` / `Cma.forecast` 都过 `cleanNow()`（`cmaNum` / `cmaStr` 按值清哨兵，
  `cmaStamp` 自己解析 `YYYY/MM/DD HH:MM` 而不是丢给 `new Date`，
  超过 `CMA_STALE_MS`（24h）也当没有），洗完没有可用温度就返回 `null` ——
  两处兜底自动接管，实况随之退回 Open-Meteo。
  顺带修掉另一个谎：原来只要 `d.now` 存在就打「中国气象局实况 + 时分」，
  会把一年前的 `2025/08/08 10:25` 当成"实况 10:25"显示出来；现在实况标签按 `d.now.src`
  标成「中国气象局实况」或「Open-Meteo 实况」，状态栏的数据来源列表同理。
  附带好处：算出来是 ±0.1%~2.5%，恰好落在真实股票一天的涨跌幅区间里；
  坏处是按涨幅排序基本等价于按 ΔT 排序（所有城市的分母都在 273~313 之间，差别不到 15%）。
  `chart.js` 的 `optKline` 里那个右侧百分数轴**本身是死的**（没有系列绑到 `yAxisIndex: 1`、
  也没给 `min`/`max`，ECharts 取不到 extent 就不画），分时图那个才是活的 —— 它显式设了
  `min`/`max`。改的时候两边都改了，但别指望 K 线图上能看见。
- **别把主题色调色板写死成字面量**：分时图的面积渐变原本硬编码 `rgba(255,77,79,.30)`，
  而气温线用的是 `C.up` —— 切到「美股习惯」后 `--up` 翻成绿的，于是**线是绿的、底下的面积还是红的**。
  渐变只能由 `C.up` 推导（现在有个 `withAlpha(C.up, .30)` 专门干这个）。
  同理 `C.flat` 也是从 CSS 变量 `--flat` 读的，`body.us` 翻转配色时它不受影响。
- **定位权限提示一辈子只弹一次**：`getCurrentPosition` 在页面加载时被无条件调用，用户随手点掉
  或拉黑之后就永久 `denied`，再点"定位"也只是立刻失败（看起来像"点了没反应"）。
  正确做法是加载时先用 `navigator.permissions.query({name:'geolocation'})` 判断，

- **全屏不要用 Fullscreen API**：iOS Safari 至今不支持 `Element.requestFullscreen`。
  用 `body.fullchart .layout{position:fixed;inset:0}` + 把其它块 `visibility:hidden`

- **ECharts 的 tooltip 会跑出容器左边**：手机上 K 线 tooltip 有十行，默认贴着数据点向右展开，
  靠左的数据点就会把左侧的「开 / 高 / 低 / 收」几行推到屏幕外（`getBoundingClientRect().left` 实测 **-32px**）。

  十行才塞得下。另外副图口径选「日内温差」时，K 线 tooltip 里的「振幅」和「日内温差」算的是同一个数
  （都是 `h - l`），窄屏直接不显示「振幅」那一行。
- **容器尺寸变了，ECharts 不会自己知道**：安卓上系统栏 inset 是**后补**到根布局 padding 上的
  （见上面 edge-to-edge 那条），WebView 视口随之变矮，但**不触发 `window.resize`** —— 于是
  `ResizeObserver` 看起来是唯一出路。可它在 **headless Chrome 里根本不派发**（自建一个 observer
  盯一个尺寸确实变了的容器，实测触发 **0 次**），所以只靠它没法在无头环境里验证，真机上也不敢只靠它。
  现在 `chart.js` 的 `follow(el, get)` 两路都上：`ResizeObserver`（存在时挂，回调走 `U.debounce(60)`）
  **加上**启动后头 4 秒每 250ms 轮询对账一次。`apply()` 里用
  `Math.round(r.width)+'x'+Math.round(r.height)` 当 key 去重，并且
  **`!r.width || !r.height` 时直接返回** —— 容器隐藏时 resize 会把 ECharts 设成 0×0，等它再显示回来就是一片空白。
  修之前：把主图容器压矮 70px（模拟 inset 后补），容器 170→100 而实例仍量到 170，
  canvas 越界 70px，正好压在副图页签行上（用户说的"主图曲线溢出到副图选单"）。修之后越界 0px。
- **d8 崩在非静态内部类上**：`build-tools 34` 的 R8 8.2.2 处理"继承 `android.jar` 里某个类、
  且带合成 `this$0` 字段的嵌套类"时抛 `NullPointerException: Cannot invoke "String.length()"`。

  `targetSdkVersion="35"`，从 Android 15 起系统对这类应用**强制 edge-to-edge** ——
  窗口铺满整屏、状态栏浮在页面之上。于是 `getWindow().setFlags(FLAG_FULLSCREEN, 0)`
  变成 no-op（状态栏不再被隐藏），WebView 从屏幕最顶端开始布局，第一行被状态栏盖掉一截

  页面侧拿不到状态栏高度。正确做法是让原生侧把系统栏高度变成根布局的 padding：

  bottom 还要与 `Type.ime()` 取 `max`（edge-to-edge 下 `adjustResize` 不再改变窗口大小，
  键盘只能靠 padding 让位），值变化时 `setPadding(0, top, 0, bottom)`，

  自己又按 safe-area 处理一遍 → 双倍留白）。
  用**实际收到的 inset** 而不是写死高度，所以低版本 Android 或状态栏真被隐藏时 inset 为 0，

  **退了 3 小时**（`i0` 再退 1 小时），又拿这个滞后的时次去算 `today` —— 于是**北京时间
  00:00~04:00 之间 `today` 会落到前一天**，副图整个取数窗口前移一天，白天却完全正常。
  这类"只在特定时段复现"的 bug，只能靠**探针把两边的横轴参数都打出来逐项对比**
  （`L/R`、`gap`、`interval`、首末类别、`dataZoom` 区间），肉眼看截图很容易漏。
  顺带：`optSub` 的 `bottom` 原来是 6，把 x 轴标签裁掉了，改成 26。
- **横排的 segmented 按钮要 `flex:none` + `white-space:nowrap`**：否则窄屏上按钮会被压扁，
  把「华南」这种两字标签折成两行，整条工具栏高度翻倍。
- **别用 `python -c "..."` 从 PowerShell 传含引号的脚本**：PS 会把内层双引号吃掉，
  Python 收到 `open(p,encoding=utf-8)` 这种残缺代码 → `SyntaxError`。
  改文件要么写成 `.py` 再跑，要么用 `[IO.File]::ReadAllText` + `.Replace()` + `WriteAllText`。
- **A 股配色反转必须靠 CSS 变量**：`body.us` 只是把 `--up` / `--down` 两个变量的值对调，
  所有图表和列表都读变量，就不用改 JS。
- **单站雷达没有任何入口页**：气象局的雷达产品有三层，全国拼图 `chinaall.html` 和八个大区
  都在导航里有链接，**独独第三层「单站雷达」没有入口** —— `chinaall.html` 里只链了全国、
  八个大区，外加北京大兴一个样例。其它城市的页面只能靠拼 slug 猜：
  `/publish/radar/{省拼音}/{市拼音}.htm`（`guang-dong/guang-zhou.htm`、`hei-long-jiang/ha-er-bin.htm`、
  直辖市是 `tian-jin/tian-jin.htm`）。所以有了 `tools/radar_slugs.py`：用 pypinyin 生成候选、
  逐个探测、把命中的写进 `web/data/radar-cities.json` 供前端读（45 城命中 30）。
  站号形如 `AZ9200`，图片是 `image.nmc.cn/product/{Y}/{m}/{d}/RDCP/{tier}SEVP_AOC_RDCP_SLDAS3_ECREF_AZ####_L88_PI_{ts}00000.PNG`。
- **`if (!x)` 改成 `if (x === undefined)` 是会出事的**：雷达抽屉的 `open()` 原来传
  `openRadar(this._radarReg)`，首次打开时 `_radarReg` 是 `null`；我把守卫从「假值判断」
  收窄成 `region === undefined` 之后，`null` 不再命中，于是跳过了「按城市自动选区」，
  直接拿 `region = null` 去拼 URL，每一帧都变成 `..._ECREF_null_...` 全 404，
  界面显示的是"中国气象局该时段没有发布"——**一个纯前端的逻辑错误伪装成了数据源故障**。
  教训：收窄相等性判断时，先想清楚所有"没有值"的表示（`undefined` / `null` / `''` / `0`）
  分别会走到哪。
- **ECharts 的 tooltip 默认可以画到容器外面**：`confine` 不设就是 `false`，触发点靠边时
  它算出来的 `left` 可以是负的，整个信息框被屏幕边缘切掉一截。手机竖屏主图只有 383px 宽，
  用户报的"信息窗格在某些位置会被遮挡无法看到全貌"就是这个（实测 `left = -32`）。
  三处 tooltip（主图、天气副图、台风路径）全部补了 `confine: true`。
  另外窄屏（`innerWidth <= 660`）还跟着收紧了字号和内边距 —— K 线 tooltip 有十来行，
  能到 215px 高，比容器本身（窄屏 `min-height` 只有 170px）还高，`confine` 只能把它按在
  容器左上角，仍然冒出去。顺带把「振幅」那一行在副图口径是「日内温差」时去掉了
  （两者算的都是 最高-最低，同一个数显示两遍）。
- **只挂 `window.resize` 不够，容器自己变了尺寸 ECharts 不会知道**：安卓 APP 启动时
  系统栏的 inset 是在 WebView 建好**之后**才补到根布局上的，容器会"先高后矮"，
  而页面不一定收到 `window.resize`。于是 ECharts 一直按旧高度画，画布溢出到下面副图的
  页签行上（用户报的"主图曲线溢出到副图选单"，实测容器 170→100 时画布越界 70px）。
  修法是 `web/js/chart.js` 的 `follow(el, get)`：**ResizeObserver + 启动后头 4 秒每 250ms
  对一次账**，加上 init 里原有的 `window.resize`，三管齐下。
  为什么不能只靠 ResizeObserver —— **headless Chrome 里它压根不派发**：自建一个 observer
  盯一个尺寸确实变了的容器，触发 **0 次**。手机端应该没问题，但既然验证不了，就不能把
  正确性押在它身上。注意 `follow` 里容器 rect 为 0 时必须直接返回：隐藏期间 resize 会把
  ECharts 设成 0×0，再显示回来就是一片空白（`app.js` 里那几处 `setTimeout` resize 就是为这个加的）。

- **同一个元素挂两个尺寸类，窄屏那条会赢**：操盘手的 `#ggEqChart` 同时写着 `.gg-chart`
  和 `.gg-chart-sm`。桌面端 `.gg-chart{flex:1}` 被后面的 `.gg-chart-sm{flex:1;height:auto}`
  覆盖，没事；但窄屏那条写的是 `.gg-chart{height:206px;flex:none}`，它把权益图也拉成
  206px，而外层 `.gg-eq` 只有 112px —— 画布比容器高 **94px**，正好压在右边的账户明细上
  （实测 `重叠=0` 之前是 -94）。修法是在窄屏那一段里给 `.gg-chart-sm` 补一条
  `height:auto;flex:1;min-height:0`，把嵌套那张还给自己的容器。教训：**给"通用尺寸类"
  写固定高度前，先确认没有别的元素也在用这个类。**
- **ECharts 的横轴标签个数别写死**：操盘主图原来是 `interval: round(n/8)-1`，桌面看着正好，
  手机竖屏（绘图区才 ~290px、一个 `D1 08:00` 标签约 52px）8 个标签直接糊成一团，
  实测连成 `D1 04:00D1 08:00D1 12:00…` 一长串。改成按容器宽度算
  `want = max(3, floor(容器宽 / 62))`，再配 `hideOverlap: true`。同理 `tooltip` 要 `confine: true`，
  否则靠边的点会算出负的 left、把左侧几列标签切掉。
