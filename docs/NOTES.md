## 那个「突然拉到底」是怎么来的

`shock` **不是随机数**。它的触发条件是**真实观测到的剧烈变化** —— 某一根 15 分钟里
CAPE 炸了、阵风猛增、或者开始下暴雨，`sev` 就会跳一大截，超出的部分变成一记冲击。
系数是拿广州 / 哈尔滨 92 天的真数据调的，调完之后：

| | 基线（没有冲击） | 现在 |
| --- | --- | --- |
| 单根涨跌 中位 | 0.169% | **0.190%**（平时盘感基本没变） |
| 单根涨跌 p99 | 3.06% | **6.28%** |
| 连续 3 根最大跌幅 中位 | 4.4% | **7.3%** |
| 连续 3 根最大跌幅 p90 / 最大 | 4.9% / 5.9% | **8.2% / 9.7%** |
| 出现过 3 根跌 ≥8% 的局面 | — | **14 / 60 局** |

`shock` 是「这一刻打多狠」，`carry` 是「余波还走多远」。只有 `shock` 的话就出一根长阴、
下一根立刻回弹，不像崩盘；加上 `carry`（按 0.78 衰减的动量）才有连续几根顺势砸下去的样子 ——
这就是《FX 战士久留美》第一话开头那种「蜡烛图突然拉到底」。

**所以没有真实天气过程的时候，盘面就是平静的。** 平静的时候你赚不到钱，
也正是这种时候最容易上杠杆，然后被一次对流爆发带走。

## 系数是调出来的，不是拍的

`50 / 16` 这两个数拿真数据（广州 / 哈尔滨各 92 天）试出来的，目标是让行情「走得动、但不变成随机数」：

| 指标 | 实测（广州） |
| --- | --- |
| 单根 15 分钟涨跌 | 中位 **0.19%**、p99 **6.3%**、最大 **10.6%** |
| 单日振幅 | 中位 **12.7%**（五天分别是 5.2% / 9.5% / 18.2% / 12.7% / 15.0%） |
| 指数区间 | 937 ~ 1110（基准 1000） |

对比过几组：`A=30,B=10` 只有日均振幅 5.5%，`A=40,B=15` 到 7.7%；
而单纯加大噪声（`scale=40, EMA a=0.5`）能到 12.3%，但曲线是**纯噪声、没有趋势可骑**。
`50/16` 是两头都占住的那组。

突发行情那一组也对比过四档：`AT=1.2 K=22` 太温和（3 根跌最大只有 8%），
`AT=0.8 K=30` 太频繁（每局 5.7 次单根 >6%，盘面变成噪声），
最后取 **`AT=0.9 K=34 decay=0.78`** —— 中位不变、极端值够狠、每局大约出现一次。

**一个测试指标上的坑**：一开始我用「单日振幅」和「10 根窗口内最大行程」衡量刺激程度，
加完冲击发现几乎没变 —— 因为这两个指标都被趋势主导了。真正区分「突然拉到底」的是
**连续 3 根 / 5 根的最大跌幅**，换成这个指标差异立刻就出来了。测错了指标会得出「改了没用」的错误结论。

## 几个实现上的选择

- **界面不显示真实日期**，只显示「第 3 天 14:15」。否则去翻历史天气就知道后面怎么走，
  这局就没得玩了 —— 取样窗口是随机的，连开两局不会是同一段。
- **它是铺满整个视口的，不是一个居中对话框**。最初写成
  `width: min(1180px,100%)` 的居中面板，在 1600 宽的屏上四周会露出一圈主站 ——
  用户看到的观感是「怎么只有屏幕中间那块变成 K 线了，主站的曲线还在」。
  改成 `inset:0` + `width/height:100%` 之后主站一点都看不见，才像个正经交易终端。
- **顶上有条 MT4/MT5 那样的行情条**（品种 / 15M / 买卖价 / 点差 / 行情时间 / 连接状态），
  右侧价格轴上贴着**现价标签**，大号下单键上直接印着现价 —— 这几个都是真交易终端看惯了的东西，
  少了就觉得"不像"。其中「点差」显示的是**真实成本**（一手开+平两次手续费折算成指数点），不是摆设数字。
- **下单前先让你看清这一单有多大**：名义仓位 / 开仓手续费 / **约可承受反向波动 X%** 三行，
  下面还有「成交记录」。这三行是照 bilibili 那个「FX 简单!」的下单卡搬的 ——
  它把「杠杆」和「仓位」两件事合成了一个数字交给你，比只显示一个「30%」有用得多：

  | 杠杆 | 10% 仓 | 30% 仓 | 50% 仓 | 满仓 |
  | --- | --- | --- | --- | --- |
  | 1× | 993% | 324% | 191% | 90.4% |
  | 10× | 99.4% | 32.5% | 19.1% | 9.03% |
  | 20× | 49.7% | 16.2% | 9.53% | 4.52% |
  | 100× | 9.93% | 3.24% | 1.90% | **0.90%** |

  推导：开仓后现金 `C`、保证金 `M = 手数·价·LOT÷N`，爆仓时 `C + 手数·Δp·LOT = M·10%`，
  所以 `Δp = (M·10% − C) ÷ (手数·LOT)`。满仓时它化简成 `(1−10%) ÷ N`，
  和上面那张表最后一行对得上（20× 实测 4.517%，理论 4.500% —— 差的那点来自手数向下取整）。
- **行情是"滚动揭示"的**：主图只画 `G.i` 之前的 K 线，跟真行情一样右端在走。
  而且**只画最近一屏**（`visBars()` 按容器宽 ÷ 9px 算，跟真实操盘软件一样自动滑动）——
  960 根全塞进 1300px 的话一根才 1.3px，蜡烛会糊成一条线。
- **两根均线 + 十字光标读数**：MA5 / MA20，鼠标在图上来回划时左上角那行
  `开 高 低 收 + MA5 + MA20` 跟着走（TradingView / MT4 的图例就是这样）。
  均线要**拿整段 `series` 算完再切可视段** —— 只拿可视段算的话，每次窗口滑动
  均线都会整体跳一下，看着像在抽搐。
- **上下影线是建模的，不是实测的**。15 分钟粒度拿不到根内的真实最高最低：
  开盘价 = 上一根收盘、收盘价 = 本根指数（这两个都是真采样），
  影线按 `|本根涨跌| × 0.30` 补出来。这条别说成"全真数据"。
- **天气闪报**：雷暴 / CAPE ≥ 3000 / 阵风 ≥ 25 / 短时强降水 / 天气转好时会从顶上滑下一条横幅，
  数值都是当根 K 线的真值（`newsAt(i)`）。同一个事件不重复播。
- 音效是 WebAudio **现场合成**的（`beep(freq, dur, type, vol)`），不引任何音频文件；
  爆仓时另外 `navigator.vibrate([80,60,220])`。
- 键盘 `↑`/`W` 做多、`↓`/`S` 做空、`空格` 平仓。
- 权益曲线画的是**账户权益**（`现金 + 浮动盈亏`）而不是余额，所以持仓期间它跟着价格跳。

## 一个数据源上的坑

Open-Meteo 的 `minutely_15` **两个主机的历史深度不一样**：

| 主机 | `past_days=92` 的结果 |
| --- | --- |
| `historical-forecast-api.open-meteo.com` | **8928 个点全部非空**（2026-07-06 → 10-06） |
| `api.open-meteo.com` | 同样 8928 个点，但**只有 6692 个非空**，更早的全是 `null` |

**只看 HTTP 状态码发现不了这件事 —— 它照样返回 200 加一串 null。**
所以 `OpenMeteo.minutely()` 先试 historical 主机，并抽查最早一天的非空比例，
低于 50% 就换主机。

## 为什么需要"三级取数"

`d1.weather.com.cn` 会**强制校验 `Referer` 必须是 `weather.com.cn`**，浏览器里补不了这个头；
`weather.cma.cn` 又会在非浏览器 UA 下返回 `406`。所以前端按下面的顺序依次尝试，谁通用谁：

```
① 本地代理（APK 自带 / 本地调试用）  →  服务端补 Referer / UA，最稳
② 浏览器直连                  →  网页版走这条；weather.cma.cn 有 CORS 头，d1 拿不到
③ 静态兜底 data/official/**   →  GitHub Actions 每 30 分钟预抓并提交的 JSON
```

网页版因此是 ② + ③：能直连的就直连，拿不到（比如 d1 的官方预报）就读仓库里 Actions 刚抓好的快照。

## Open-Meteo 的免费额度，以及为此做的节流

Open-Meteo 免费档（非商业）的硬上限是**每分钟 600 次 / 每小时 5,000 次 / 每天 10,000 次**，
**超了不会提前通知，直接封 IP**。被限流时接口返回的就是这一句：

```json
{"error":true,"reason":"Daily API request limit exceeded. Please try again tomorrow."}
```

本站绝大多数请求走的是中国天气网（`Cma.now`，无论多少城市都只读一份快照），
真正会随「城市数 × 时间」放大的是 Open-Meteo。实测方式：`?local=0` 把页面挂 2 小时
（用 `--virtual-time-budget` 压缩应用时间），从 iframe 的 Resource Timing 里数请求。
最初的构成是：

| 调用 | 次数 / 2 小时 | 说明 |
| --- | --- | --- |
| `current=` 实况兜底 | **720** | 无官方站号的城市（典型是「当前所在地」）用 Open-Meteo 当前值当报价 |
| `brief` 昨收 / 迷你走势 | 68 | 自选 + 热门，每个坐标 4 次 = 2 小时里 4 轮 |
| `past_days=92` 历史逐时 | 12 | 画日 K 用的 92 天历史 |
| `archive` / `air-quality` | 4 / 4 | 归档与空气质量 |

折合约 **9,650 次/天**，正卡在免费额度上。根因不是"请求太多"，而是
**缓存只在请求成功返回之后才写入** —— 只要一次请求还没落地（网络慢，或者上游 20 秒
的超时比 10 秒的轮询间隔还长），下一个 tick 就再发一次，于是永远存不上，退化成
「每个轮询 tick 一次」。

修法在 `web/js/api.js` 的 `getJSON()`：

- **`inflight` 表**：同一个 cache key 正在飞的请求只保留一个 Promise，后来者直接复用
- **失败也缓存**（`FAIL_TTL = 60000`）：上游 429 / 超时之后 60 秒内不再重试
- `warmQuotes()` 里 `BRIEF_MS = 1800000`（30 分钟一轮）、`BRIEF_MAX = 40`（一轮最多 40 城）；
  注意 **brief 的 TTL 必须写成和节流周期同一个值**，否则缓存先过期，节流等于没做
- 轮询间隔默认从 3 秒改成 **10 秒**（`web/index.html` 的下拉里仍可选 3 秒）

改完复测同样 2 小时：**总请求 804 → 183，其中 `current=` 720 → 103**，折合约 2,200 次/天。

轮询间隔默认设成 **15 分钟**（下拉里仍可选 1 秒 ~ 5 分钟）。因为额度是**按 IP 计**的，
被限流时接口返回的就是上面那句 429 —— 而且**只影响被限流的那台机器**，
换一台设备、换一个网络出口，额度就是全新的一份。所以调试时千万别用
`--virtual-time-budget` 长时间跑页面，那会把真实当天的额度一次性烧光。

## 额度用光时的退路：换一台 Open-Meteo 主机

免费额度是**按主机名分桶**的，这一点不看文档看不出来 —— 实测把
`api.open-meteo.com` 打到 429 之后：

| 主机 | 当时状态 |
|---|---|
| `api.open-meteo.com`（forecast） | **429** `Daily API request limit exceeded` |
| `archive-api.open-meteo.com`（archive） | 200 |
| `air-quality-api.open-meteo.com` | 200 |
| `historical-forecast-api.open-meteo.com` | **200** |

而 `historical-forecast-api.open-meteo.com/v1/forecast` 的**参数和返回结构跟主站完全一致**，
连 `past_days` + `forecast_days` 那一段未来预报都照给（实测
`past_days=92&forecast_days=16` 返回 `2026-07-06..2026-10-21`，与主站等价）。所以它就是
一个免费的备份源。三处都加了主机回退，谁行用谁，并把可用的那台记下来（`omHost`），
下次先走它，不必每次都去撞墙：

- `web/js/api.js` 的 `omGetJSON(q, opt)` —— `brief` / `forecast` / `mini` / 实况回退都走它
- `web/js/weather.js` 的 `jgetOm(q, ttl, key)` —— 逐小时那一个大请求走它
- `server/app.py` 的 `om_passthrough()` —— 本地代理 / APK 那条路也照样回退

缓存 key 末尾带 `#h<idx>`（两台主机各存各的），否则一台的失败记录会把另一台也堵住。

写这段的起因值得记一笔：**429 期间页面的表现极具误导性**。中国气象局的数据全都正常
（气温、湿度、风、气压、日 K 全部有值），只有 Open-Meteo 来的字段变成 `--`：
自选/热门列表整列涨跌幅、平均风速、日出日落、5 天落差。看上去像"功能坏了"，
实际上是二级源被限流、一级源好好的 —— 而主图和副图的横轴对齐、K 线形态这些
"看起来最像坏掉"的部分反而完全正常。

还有一个我自己埋的坑：`warmQuotes()` 里原本不管成败都写 `S.briefAt = Date.now()`，
于是一次失败（比如当天额度用光）就把整列涨跌幅**锁死半小时**，期间一次重试都没有，
额度恢复了也不会自己好。现在 `S.briefAt` 是"下次允许拉的时刻"：成功推 30 分钟，
**失败只推 2 分钟**，能自己恢复。

一个曾经踩过的坑：`OpenMeteo.archive()` 的缓存键漏了 `endDate`
（原来是 `'a|' + lat + ',' + lon + '|' + startDate`）。同一 start、不同 end 的两次调用
会互相命中缓存，第二次等于没发出去。目前只有一个调用点所以没暴露，但键该带上就带上。

## 再退一步：「昨收」改用气象局日历算

主机回退解决的是"某一台被限流"。要是两台都不通（断网，或者两家额度一起见底），
自选/热门列表那整列涨跌幅还是会全 `--`。所以昨收又加了一层**完全不依赖 Open-Meteo** 的兜底：

- `web/js/api.js` 的 `Cn.brief(city)` —— 读中国天气网的**月度日历**（就是日K页用的那套
  `calendar_new`），把**昨天**那天的**实测日均温** `(maxobs + minobs) / 2` 当作昨收，
  再用最近几天的日均温拼一条迷你走势。当月文件通常带着上月末尾几天，所以一份就够；
  万一不够（月初抓的当月文件从 1 号起）再补一份上月。
- `web/js/app.js` 的 `briefOf(city, ttl)` —— 先试 `OpenMeteo.brief`，拿不到 `prevClose`
  才走 `Cn.brief`。正常情况下**一次多余的请求都不会发**。

**两个源的「昨收」定义不一样，这是数据粒度决定的，不是 bug：**

| 源 | `prevClose` 的含义 | 粒度 |
|---|---|---|
| `OpenMeteo.brief` | 昨天最后一个整点的气温（真正的"收盘价"） | 逐小时 |
| `Cn.brief` | 昨天实测日均温 `(maxobs + minobs) / 2` | 逐日 |

所以同一个城市在兜底模式下算出来的涨跌幅，**数值会和平时有出入，偶尔连正负号都不同** ——
24 ℃ 的现价，跟"昨天 23 点 20 ℃"比是涨，跟"昨天日均 27.5 ℃"比就是跌。
这个出入可以接受（毕竟整件事就是把天气包装成行情，两边都是从真实观测算出来的），
但**别把两条线上的百分比当成同一个指标来横向比较**。

覆盖范围也是分开的：桌面版 / APK 走本地代理，`d1` 域随便抓，**352 城全都有**；
GitHub Pages 是纯静态站，只有 `tools/prefetch_official.py` 预抓过的城市才有
`data/official/cal/` 文件（当前 45 城，**热门 22 城全在其中**），其余城市在网页版上
拿不到兜底值，仍会显示 `--`。

日历里只有 `cla='obs'` 的日子带 `maxobs/minobs`（更早的是 `cla='history'`，只有历史同期
均值），所以兜底时的迷你走势通常只有**最近 5 天**。线短一点，形状是对的。

## 没有手机怎么测 APK

本机没有 `adb`、也没有连过任何安卓设备，所以"装到手机上"这一步没法自动化。
退一步，**把最容易出错的那部分单独拎出来在 PC 上跑**：APK 里真正容易被改坏的，是
`MainActivity` 里那些把中国天气网的文件解析成 JSON 的 Java 代码（正则、编码、`var` 前缀剥离）。

- `tools\test_apk_parser.py` 直接 `subprocess` 调 `D:\Java\bin\javac` / `java`，把
  `android\test\TjsParseTest.java` 编出来跑，喂进真实的抓取内容，**25 项断言**覆盖：
  `var cityDZ101010100 ={...}` 的 `var` 剥离、GBK 解码、`sk_2d` / `dingzhi` / `calendar_new`
  三种文件形态、`oot` 字段空缺、以及台风 JSONP 的双层括号。
- `android\test\` 只进仓库、**不进 APK**（`build_apk.py` 的 `SKIP_ASSET` / 编译清单都不含它）。

其余部分（WebView 装载、拦截器路由、签名）只能靠真机验证 —— 这一点在下面的
「已知限制」里如实写着。

## 一些实现上的坑（给后来的人）

- **手机窄高屏上 `flex:1` 的图表会塌成 0 高**：`.chart-box{flex:1;min-height:0}` 在高度不够时会被压到 0，
  而隔壁 `.chart-box.sub{flex:0 0 132px}` 有固定 basis 照样可见 —— 表现就是"主图不见了，页签下面直接是副图"。
  窄屏必须给 `.chart-box{flex:1 1 auto;min-height:170px}`，再把整页高度交给 `.pane-center` 内部滚动。
- **底部页签不会自己工作**：`index.html` 里 `<button class="mtab" data-mtab="N">` 只是标记，
  事件要在 `bind()` 里自己挂（`closest('.mtab[data-mtab]')` → `setMTab`）。当初只有 `setMTab`/`syncMTabs`
  和深链分支，四个按钮全是死的 —— 而且不报错，只是点了没反应。
- **ECharts 的 x 轴标签会被自己的 dataZoom 滑块盖住**：`grid(l,r,t,b)` 的 `b` 必须大于
  滑块高度 + 底部间距。`{type:'slider', height:15, bottom:5}` 占 `H-20` 往上，而 `b=34` 时
  标签正好落在 `H-26 .. H-14` —— 两者重叠。主 K 线图现在用 `b=46`。
- **ECharts 的 K 线把"平盘"当阴线**：`candlestick` 判阳线用的是**严格** `close > open`，
  `close === open` 会落进 else 分支、套用跌的 `color0`/`borderColor0`（在仓库自带的
  `echarts.min.js` 上实测确认）。气温 K 线里这种"一天下来没升没降"的日子占 **3.3%**
  （576 天里 19 天），所以凡是在别处自己判涨跌，算子必须跟它对齐 —— 量能柱原来写的是 `>=`，
  于是平盘那天会出现「**上面一根绿 K 线、下面一根红量柱**」。现在平盘统一涂中性灰：
  K 线用 per-item `itemStyle`（数组式和 `{value, itemStyle}` 对象式可以混用，
  `markPoint` 的 `valueDim: 'highest'/'lowest'` 在对象式数据下实测依然生效），
  量柱在 `data[i].itemStyle.color` 上判。
- **别拿摄氏温度当分母算"涨跌幅"**：气温是**间隔尺度**（interval scale）量 —— 零点是人为约定的
  "水的冰点"，不是"没有温度"。比值只在**比率尺度**（有真零点）上才有意义，判据很简单：
  同一件物理事实换个单位结果就变。21.0℃ → 22.5℃ 在摄氏下是 `+7.14%`、开尔文下 `+0.51%`、
  华氏下 `+3.87%`，三个数说的是同一天。股票价格是比率尺度（0 元就是真的没钱），气温不是。
  这不只是"意义可疑"，而是**会直接算错**：
  - **0℃ 以下是负的**，于是分母变号 → **涨跌方向整个反过来**。哈尔滨
    2025-12 ~ 2026-02 的 90 个交易日里，收盘价在 0℃ 以下的有 **88 天（98%）**，
    其中 **47 天**是"升温却显示成负数"；最离谱的 2025-12-23 开 `-4.8`、收 `-16.1`
    （大降温 11.3℃）却显示 **`+235.4%`**，2026-02-22 开 `5.9`、收 `-10.9` 显示 **`-284.7%`**。
  - **0℃ 处除零**（`1.0 / 0.0` → `Infinity`）、接近 0℃ 时爆表（`3.0 / -0.5` → `-700%`）。
  - 即使在零上，量级也不对：`pct_摄氏 / pct_开氏 = (T + 273.15) / T`，20℃ 时相差 **14.7 倍**，
    广州 +1.5℃ 显示 `+7.14%`、武汉 +7.1℃ 显示 `+39.35%` —— 放在炒股壳子里非常违和。

  所以统一改成 `U.pctOf(cur, base) = (cur - base) / (base + 273.15) * 100`，
  凡是"气温 / 气温"的地方全部走它：行情头、指数条、自选列表、K 线 tooltip、分时 tooltip、
  分时右侧百分数轴、以及 BOLL 带宽（`indicators.js` 的 `(上轨-下轨)/中轨`）。
  **KDJ 的 RSV、RSI、WR 不用动** —— 它们的分母是**温差**（`hh - ll`）或涨跌绝对量之和，
  本来就与零点无关。**BOLL 带宽要动**（`(上轨-下轨)/中轨`，中轨是气温均值）：
  中轨为负时带宽会变成**负数**（-10℃ 附近实测 **-144%**、-2℃ 附近 **-787%**、
  +2℃ 附近又翻成 **+641%**），穷举中心 -40~45℃ 的 3526 个取值，改完之后
  非正/非有限值 **0 个**，全部落在 3.6%~5.4%。

  代价要知道：大气温度只在 273~313 K 之间晃，分母几乎是常数，于是比值退化成
  `ΔT × ~0.0034`，基本就是**绝对差的线性重标定**，"相对变化"那层含义没有了。
  但这正是物理上的实话 —— 对气温而言有意义的量就是绝对差 ΔT 本身。
- **月K 的键不是完整日期，别拿它算星期几**：K 线 tooltip 的标题原来是
  `b.d + ' ' + weekday(b.d)`。日K 的 `b.d` 是 `'2026-10-06'`、周K 是那一周的周一（也是完整日期），
  都没问题；但月K 的键只有 `'YYYY-MM'`（`indicators.js` 的 `keyOf` 返回 `d.d.slice(0, 7)`），
  而 `U.parseDate` 是 `new Date(+p[0], +p[1] - 1, +p[2])` —— `p[2]` 是 `undefined`、`+undefined` 是 `NaN`，
  于是 `new Date(2025, 10, NaN)` 得到 **Invalid Date**，`getDay()` 返回 `NaN`，
  最后 `'周' + w[NaN]` 就是 **`周undefined`**（用户看到的就是标题写着 `2025-11 周undefined`）。
  **JS 在这里一声不响**：数组下标是 `NaN` 只返回 `undefined`，拼进字符串就成了给用户看的东西，
  既不报错也没有 `TypeError` 兜底。
  修法是两头都收一下：`U.weekday()` 拼不出星期几时返回**空串**而不是 `'周undefined'`
  （判据是 `d.getDay()` 的 `NaN` 自己不等于自己），tooltip 标题改走一个 `tipTitle(d)` ——
  有星期几就写 `2026-10-06 周二`，只有年月就写 `2025 年 11 月`，别的原样输出。
  同一族的问题还有一处：周K / 月K 是**聚合**出来的，`indicators.js` 只带了
  `{d,o,h,l,c,v,n,raw}`，没有 `range` / `windAvg` / `humAvg`，于是量能那一行固定显示
  `日内温差 -- ℃`（月K 下副图本来就是隐藏的）。现在取不到就**整行不显示**，
  而不是画一行占位的破折号 —— 日K 那行不受影响（实测 553 根全有值）。
- **气象局的"没有观测"是 `9999`，不是 `null`**：`weather.cma.cn` 对没有实时观测的站，
  会把**每一个**字段都填成哨兵 —— 数值字段给 `9999`、字符串字段给 `"9999"`、
  `lastUpdate` 停在最后一次正常上报的时刻（不是空、不是 0、更不是当前时间）。
  实测澳门（`45011B`）的 `lastUpdate` 是 **2025/08/08 10:25**（一年前）、
  台北（`58968`）是 **2025/04/23 21:17**，`data.now` 里 9 个字段全 9999；
  而同一时刻广州（`59287`）的 `lastUpdate` 是 `2026/10/06 10:00`，字段全是真值。
  最容易漏掉的是它**不只出现在港澳台**：Actions 预抓的 40 份静态 `data/official/cma/*.now.json`
  里有 **6 份**带 9999 —— 除澳门/台北外还有 **上海（`58367`）/ 郑州（`57083`）/
  株洲（`57780`）/ 成都（`S1003`）**（成都的站号甚至是非数字的），
  而这几个站**打实时接口会返回正常值** —— 说明 9999 是**偶发**的。
  所以过滤必须**按值判**，不能按城市白名单，也不能只靠"这个站是不是港澳台"。
  `web/js/api.js` 的 `Cma.now()` 原来把上游字段原样透传，于是哨兵变成了"真温度"：
  - `Store.quote()` 里写的是 `if (n && n.temp != null) return n;` —— `9999.0 != null` 成立，
    于是哨兵被收下，而且**永远走不到下面的 Open-Meteo 兜底**；
  - 详情头 `quoteOf()` 又**优先**取 `S.quotes[id].temp` 而不是中国天气网快照，
    于是表现成「**搜索时看着正常、一加入自选就炸**」：加入自选后列表轮询把 `q.temp = 9999`
    填了进去，涨幅变成 `9999 - 23.9 = 9975.1`、`9975.1 / (23.9 + 273.15) ≈ +3358%`，
    湿度 `9999%`、风速 `9999 m/s`、气压 `9999 hPa`、体感 `9999.0℃`、风向 `9999` 一起炸，
    9999 还会在自选按涨幅排序时顶到最上面。
  现在 `Cma.now` / `Cma.forecast` 都过 `cleanNow()`（`cmaNum` / `cmaStr` 按值清哨兵，
  `cmaStamp` 自己解析 `YYYY/MM/DD HH:MM` 而不是丢给 `new Date`，
  超过 `CMA_STALE_MS`（24h）也当没有），洗完没有可用温度就返回 `null` ——
  两处兜底自动接管，实况随之退回 Open-Meteo。
  顺带修掉另一个谎：原来只要 `d.now` 存在就打「中国气象局实况 + 时分」，
  会把一年前的 `2025/08/08 10:25` 当成"实况 10:25"显示出来；现在实况标签按 `d.now.src`
  标成「中国气象局实况」或「Open-Meteo 实况」，状态栏的数据来源列表同理。
  附带好处：算出来是 ±0.1%~2.5%，恰好落在真实股票一天的涨跌幅区间里；
  坏处是按涨幅排序基本等价于按 ΔT 排序（所有城市的分母都在 273~313 之间，差别不到 15%）。
  `chart.js` 的 `optKline` 里那个右侧百分数轴**本身是死的**（没有系列绑到 `yAxisIndex: 1`、
  也没给 `min`/`max`，ECharts 取不到 extent 就不画），分时图那个才是活的 —— 它显式设了
  `min`/`max`。改的时候两边都改了，但别指望 K 线图上能看见。
- **别把主题色调色板写死成字面量**：分时图的面积渐变原本硬编码 `rgba(255,77,79,.30)`，

  **退了 3 小时**（`i0` 再退 1 小时），又拿这个滞后的时次去算 `today` —— 于是**北京时间
  00:00~04:00 之间 `today` 会落到前一天**，副图整个取数窗口前移一天，白天却完全正常。
  这类"只在特定时段复现"的 bug，只能靠**探针把两边的横轴参数都打出来逐项对比**
  （`L/R`、`gap`、`interval`、首末类别、`dataZoom` 区间），肉眼看截图很容易漏。
  顺带：`optSub` 的 `bottom` 原来是 6，把 x 轴标签裁掉了，改成 26。
- **横排的 segmented 按钮要 `flex:none` + `white-space:nowrap`**：否则窄屏上按钮会被压扁，
  把「华南」这种两字标签折成两行，整条工具栏高度翻倍。
- **别用 `python -c "..."` 从 PowerShell 传含引号的脚本**：PS 会把内层双引号吃掉，
  Python 收到 `open(p,encoding=utf-8)` 这种残缺代码 → `SyntaxError`。
  改文件要么写成 `.py` 再跑，要么用 `[IO.File]::ReadAllText` + `.Replace()` + `WriteAllText`。
- **A 股配色反转必须靠 CSS 变量**：`body.us` 只是把 `--up` / `--down` 两个变量的值对调，
  所有图表和列表都读变量，就不用改 JS。
- **单站雷达没有任何入口页**：气象局的雷达产品有三层，全国拼图 `chinaall.html` 和八个大区
  都在导航里有链接，**独独第三层「单站雷达」没有入口** —— `chinaall.html` 里只链了全国、
  八个大区，外加北京大兴一个样例。其它城市的页面只能靠拼 slug 猜：
  `/publish/radar/{省拼音}/{市拼音}.htm`（`guang-dong/guang-zhou.htm`、`hei-long-jiang/ha-er-bin.htm`、
  直辖市是 `tian-jin/tian-jin.htm`）。所以有了 `tools/radar_slugs.py`：用 pypinyin 生成候选、
  逐个探测、把命中的写进 `web/data/radar-cities.json` 供前端读（45 城命中 30）。
  站号形如 `AZ9200`，图片是 `image.nmc.cn/product/{Y}/{m}/{d}/RDCP/{tier}SEVP_AOC_RDCP_SLDAS3_ECREF_AZ####_L88_PI_{ts}00000.PNG`。
- **`if (!x)` 改成 `if (x === undefined)` 是会出事的**：雷达抽屉的 `open()` 原来传
  `openRadar(this._radarReg)`，首次打开时 `_radarReg` 是 `null`；我把守卫从「假值判断」
  收窄成 `region === undefined` 之后，`null` 不再命中，于是跳过了「按城市自动选区」，
  直接拿 `region = null` 去拼 URL，每一帧都变成 `..._ECREF_null_...` 全 404，
  界面显示的是"中国气象局该时段没有发布"——**一个纯前端的逻辑错误伪装成了数据源故障**。
  教训：收窄相等性判断时，先想清楚所有"没有值"的表示（`undefined` / `null` / `''` / `0`）
  分别会走到哪。
- **ECharts 的 tooltip 默认可以画到容器外面**：`confine` 不设就是 `false`，触发点靠边时
  它算出来的 `left` 可以是负的，整个信息框被屏幕边缘切掉一截。手机竖屏主图只有 383px 宽，
  用户报的"信息窗格在某些位置会被遮挡无法看到全貌"就是这个（实测 `left = -32`）。
  三处 tooltip（主图、天气副图、台风路径）全部补了 `confine: true`。
  另外窄屏（`innerWidth <= 660`）还跟着收紧了字号和内边距 —— K 线 tooltip 有十来行，
  能到 215px 高，比容器本身（窄屏 `min-height` 只有 170px）还高，`confine` 只能把它按在
  容器左上角，仍然冒出去。顺带把「振幅」那一行在副图口径是「日内温差」时去掉了
  （两者算的都是 最高-最低，同一个数显示两遍）。
- **只挂 `window.resize` 不够，容器自己变了尺寸 ECharts 不会知道**：安卓 APP 启动时
  系统栏的 inset 是在 WebView 建好**之后**才补到根布局上的，容器会"先高后矮"，
  而页面不一定收到 `window.resize`。于是 ECharts 一直按旧高度画，画布溢出到下面副图的
  页签行上（用户报的"主图曲线溢出到副图选单"，实测容器 170→100 时画布越界 70px）。
  修法是 `web/js/chart.js` 的 `follow(el, get)`：**ResizeObserver + 启动后头 4 秒每 250ms
  对一次账**，加上 init 里原有的 `window.resize`，三管齐下。
  为什么不能只靠 ResizeObserver —— **headless Chrome 里它压根不派发**：自建一个 observer
  盯一个尺寸确实变了的容器，触发 **0 次**。手机端应该没问题，但既然验证不了，就不能把
  正确性押在它身上。注意 `follow` 里容器 rect 为 0 时必须直接返回：隐藏期间 resize 会把
  ECharts 设成 0×0，再显示回来就是一片空白（`app.js` 里那几处 `setTimeout` resize 就是为这个加的）。

- **同一个元素挂两个尺寸类，窄屏那条会赢**：操盘手的 `#ggEqChart` 同时写着 `.gg-chart`
  和 `.gg-chart-sm`。桌面端 `.gg-chart{flex:1}` 被后面的 `.gg-chart-sm{flex:1;height:auto}`
  覆盖，没事；但窄屏那条写的是 `.gg-chart{height:206px;flex:none}`，它把权益图也拉成
  206px，而外层 `.gg-eq` 只有 112px —— 画布比容器高 **94px**，正好压在右边的账户明细上
  （实测 `重叠=0` 之前是 -94）。修法是在窄屏那一段里给 `.gg-chart-sm` 补一条
  `height:auto;flex:1;min-height:0`，把嵌套那张还给自己的容器。教训：**给"通用尺寸类"
  写固定高度前，先确认没有别的元素也在用这个类。**
- **ECharts 的横轴标签个数别写死**：操盘主图原来是 `interval: round(n/8)-1`，桌面看着正好，
  手机竖屏（绘图区才 ~290px、一个 `D1 08:00` 标签约 52px）8 个标签直接糊成一团，
  实测连成 `D1 04:00D1 08:00D1 12:00…` 一长串。改成按容器宽度算
  `want = max(3, floor(容器宽 / 62))`，再配 `hideOverlap: true`。同理 `tooltip` 要 `confine: true`，
  否则靠边的点会算出负的 left、把左侧几列标签切掉。

## 加那四个「压力源」时踩的坑

### 取数：四个源各有一个必须先知道的事

- **`air-quality-api` 的 `minutely_15` 是不存在的**。参数照收、HTTP **200**，但返回的
  `time` 数组长度是 **0** —— 只看状态码永远发现不了。所以 PM2.5 只能走 `hourly` +
  `past_days=92`（实测 2232 个点全非空），再按小时键对齐到 15 分钟根。
  同类陷阱还有一个：`past_days=92` 在气象主接口上会让你以为拿到了 92 天，
  实际上超出范围的部分是**一串 `null`**，长度对、内容是空的。
- **`previous-runs-api` 的用法藏在变量名后缀里，不在参数里**。要拿"提前 24 小时的预报"
  得请求 `temperature_2m_previous_day1`；所有 `models=xxx_previous_dayN` 的写法都会
  **HTTP 400 `Cannot initialize MultiDomains from invalid String value`**。
  更坑的是：**不加后缀时它返回的数据与 `historical-forecast-api` 一模一样**
  （864 个时刻逐点相同），很容易让人得出结论"这个 host 只是个别名，没用"，然后放弃。
- **台风的列表是倒序的**。`list_<年>` 按新→旧排，只取前 12 个拿到的是最近几个月，
  而 92 天窗口里真正逼近华南的那几个（沙德尔 211km / 紫檀 350km / 美莎克 477km）
  全在 7~8 月，被整段切掉。改成取 **30** 个之后，探针里的路径点从 384 涨到 1557。
- **CORS 响应头只在请求带 `Origin` 时才返回**。测数据源可用性的第一轮没带 `Origin`，
  结果**连已经在用的 `api.open-meteo.com` 都被测成"没有 CORS"**，差点据此否掉一堆能用的源。
  带上 `Origin: https://lolikonnn.github.io` 重测，五个源全是 `*`。
  另外 `dict(r.headers)` 保留服务端原始大小写，取 CORS 要大小写不敏感地遍历。

### 对齐：用时间差，不要用数组下标

四个源的时间轴各不相同（15 分钟 / 逐小时 / 事件型 / 台风路径点）。统一用

```js
const BAR_MS = 900000;
const barT0 = mn.time.length ? Date.parse(mn.time[0]) : 0;
const idxOf = t => (barT0 && t) ? Math.round((t - barT0) / BAR_MS) : -1;
```

用**差值**定位根号。这样浏览器把 `mn.time`（`2026-07-06T00:00` 这种不带时区的串）
解释成哪个时区都不影响结果 —— 因为两端用的是同一个解释。
按数组下标对会整体错位，按"把时间串截断成小时"对则在跨天/跨时区时出问题。

### 播报：状态量必须只在上升沿播

第一版直接在 `newsAt()` 里判 `if (s.gust >= 32)` 这类条件。跑一局（当时是 960 根，
现在一局是 672 根 15 分钟），探针打出 **台风播报 540 次** —— 台风影响持续几十个小时，
每一根都满足条件。

现在全部走两个辅助：

```js
const prev = G.seeds && G.seeds[i - 1];
const rise = (f, th) => s[f] >= th && !(prev && prev[f] >= th);
const fall = (f, th) => s[f] <= th && !(prev && prev[f] <= th);
```

只有**第一次越过阈值**才播。改完之后一局里台风只剩 4~5 条、地震 0~1 条，
其余是天气与盘子消息，总数约 30 条。雷暴这种用天气码判的，也一样要判前后
（`stormy(wc) && !stormy(prev.wcode)`）。

### 窗口：事件型的数据不能纯随机切

92 天里台风拢共就那么几次，纯随机切一段 7 天的窗口，大多数局里四项里有两三项覆盖率是 0 —— 
功能写了跟没写一样。加了 `biasedStart()`：撒 40 个候选起点，每 7 根验一个洞、
每 4 根累加 `|地震项| + |台风项|`，**50% 的局挑分最高的那十天、50% 纯随机**。

这里有个刻意的取舍：**不做成"每局必有事件"**。那样就变成安排好剧情，
而整个游戏的前提是"你不知道这段是哪年月"。

### 调参：量出来再改

`QUAKE_K` / `FCST_K` / `TYPHOON_K` 各改过一轮，依据是探针跑 10 局打的分布：

| 参数 | 第一版 | 症状 | 改成 |
| --- | --- | --- | --- |
| `FCST_K` | 7 | 预报项 `min=-59.5 max=+54.8`，±6% 的抖动全来自预报误差 | **2** |
| `QUAKE_K` | 6 | M4.6 / 653km 只值 0.64 点，等于没有 | **12** |
| `TYPHOON_K` | 60 | 211km / 52m/s 直接顶到 60 点 | **40** |

### 两个把"模块整个挂掉"的声明错误

- **`pad2` 重复声明**：`wxui.js` 顶部（第 16 行）已经有
  `const pad2 = n => (n < 10 ? '0' : '') + n;`，写地震面板时又在底部
  `function pad2(v) { ... }` —— 同一个 IIFE 作用域里重复声明，整个文件抛
  `SyntaxError: Identifier 'pad2' has already been declared`，**`WXUI` 直接挂不上**。
  表面症状是"点地震按钮没反应"，而且 `window.onerror` 收集到的那条错在控制台里
  一点不起眼。教训：往一个大文件底部加工具函数前，先 `grep` 一下名字。
- **`window.APP` 与 `window.__APP`**：主站全局只有一个带双下划线的 `__APP`。
  新写的 `openQuake()` 里写了 `global.APP`，于是它**恒为 `null`**，
  面板永远显示"先选一个城市，地震按离它的距离筛"—— 看着像"没选城市"，
  其实是变量名写错。同一个文件里其它地方（`wxui.js:343`）用的都是 `window.__APP`，
  照抄邻居就不会错。

### 无头验证的三个坑

- **`WXUI.open()` 不是 `async`**，它内部 fire-and-forget 地调 `openQuake()`。
  探针里写 `await wx.open('wxQuake')` 会立刻返回，读到的是"正在拉取…"那张占位卡。
  要确定性地等，必须**直接 `await wx.openQuake()`**。
- **`--virtual-time-budget` 下 `Date.now()` 也是虚拟的**。探针里那种
  `while (Date.now() < t0 + 60000) { await sleep(300) }` 的等待循环会在几毫秒真实的
  时间里跑完 60 秒虚拟时间，**在真实网络请求返回之前就超时退出**。
  改成直接 `await` 那个真异步函数才是对的。
- **截图会抓到抽屉开合动画的中间帧**：第一次截出来的面板宽度只有一半、文字还没上屏，
  看着像"样式没生效"。加一个 `?simple=1` 模式（只渲染、不做后续边界测试、
  最后 `setTimeout` 停 3 秒）再截就正常了。**判 CSS 有没有生效不要靠截图** —— 
  直接打 `getBoundingClientRect()` 和 `getComputedStyle()`，

  ```
  <span class="wx-qk-mag"> rect=276,140 36x17 color=rgb(26,20,0) fs=11px vis=visible
  ```

  这样量出来的数据比图可信。

### 主站地震面板为什么用 USGS

用户说「地震源的数据要是能找到记得在网站主页面补上相关功能」，于是主站也加了 🌋 面板。
选源的时候试过中国地震台网：`www.ceic.ac.cn` 响应是 **200**、内容也有，但
**不带 CORS 头**，浏览器里 `.fetch()` 直接读不到。USGS 的
`fdsnws/event/1/query` 免 key、CORS 全开、按半径筛，所以用它。

距离算法在 `wxui.js` 里**单独写了一份**（`qkDist`），**故意不去 import `game.js` 的 `distKm`** ——
主站天气页的模块不该因为一个函数去依赖游戏模块。两份实现都是标准 haversine，
各 8 行，重复的代价远小于耦合的代价。

## 加六档 K 线周期时踩的坑

用户说「能改成 1 分钟一根 K 线、5 分钟一根 K 线…这几个档位吗，然后游戏模拟天数从 10 天改成 7 天」。
数据最细只有 15 分钟，所以六档里有四档是真数据、两档是画的。

### 一局固定 7 天的「天气时间」，跟 K 线周期解耦

速度的单位是**每真实秒推进多少分钟的天气时间**（不是"每秒几根 K 线"）。这样一局墙钟时长只跟
速度有关（11.2 / 7.6 / 3.7 / 1.9 分钟），跟挑哪一档无关 —— 挑 1 分钟只是看得更细，不会玩得更久。
如果单位改成"每秒钟几根"，那 1 分钟档一局要放 10080 根，同样时长下每根只有几毫秒，反而看不清。

**价格模型只跑一遍**：`pickSeries` 永远按 `srcBars() = 672` 根 15 分钟源数据算基准序列，
再 `resample` 到你挑的档位。这样"1 分钟档和 60 分钟档走势不一样"这种 bug 从结构上就不可能出现 ——
两者是同一根父序列的两种渲染。

### 1 / 5 分钟那两档是插值，必须说清楚

```js
// 展开分支：父根摊成 m = SRC_MIN / barMin 根
p.o + (p.c - p.o) * f + amp * 0.06 * zag(i, j)
```

- `zag(a, b)` 是**确定性**伪随机（`Math.sin((a*131 + b*17)*12.9898)*43758.5453` 取小数），
  **故意不用 `Math.random()`**：否则同一段行情每次打开长得都不一样，探针没法验收
  （"1 分钟摊出来的子根聚合回 15 分钟必须逐点相等"这条断言会随机挂）。
- **最后一根强制 `c = p.c`**，否则子根聚合回去会跟父根差一点点。
- 影线用 `amp * 0.10 * |zag(i, j+977)| + |c - o| * WICK_K`，第二项是常数 `WICK_K = 6.5`，
  能让"开收几乎相等"的平坦根也长出可见的上下影 —— 真实 K 线里不存在完全没有影线的根。

### 局中换周期：只能往回退，绝不能往前跳

换档时先把"现在"换算成天气分钟数（`(G.i + 1) * barMin()`，因为 `G.i` 是**最后一根已经走完**的
K 线，它的收盘时刻就是"现在"），再 `Math.floor(nowMin / newBarMin) - 1` 定位新档位的当前根。

**必须用 `floor` 而不是 `round`/`ceil`。** 用 `ceil` 会把 `G.i` 指到一段**还没发生**的天气的收盘价上，
`G.price` 瞬间跳到未来，中间那些根会被跳过 —— 如果玩家在那儿挂着止损，等于被"预知"扫掉了。
用 `floor` 的代价只是往回退不到一个周期（15 分钟档切 60 分钟档退 15 分钟），这个代价可以接受。

### 批处理主循环：小数累加器

`tick()` 原来一次推进一根，960 根 / 16 分钟还行。改成 1 分钟档 + 慢速之后每秒只推 1.5 根，
按 `setInterval(tick, 100)` 每帧 0.15 根，**取整永远是 0，行情直接卡死**。改成：

```js
G.acc += (SPEEDS[G.speedIdx] / barMin()) / TICK_HZ;
let step = Math.floor(G.acc);
if (step < 1) return;
G.acc -= step;
```

一帧内推进多根，但**只 `render()` 一次**（否则狂暴速度下每秒渲染 60 次，
图表重绘会把主线程占满）。闪报只取批内最后一条，不然飘字会糊满屏幕。

### 无头探针的几个坑

- **`Game._t` 里没有 `G`**：`G` 挂在顶层 `Game.G` 上。探针写 `T.G.barIdx = 3` 会报
  `Cannot set properties of undefined`。`barMin()` 同理，是模块函数不是 `G` 的方法。
- **跨周期比较必须先钉住 `Math.random`**：`pickSeries` 里的窗口偏置 `biasedStart` 用
  `Math.random()` 挑起点。要比较"六档是不是同一段天气"，得先把 `Math.random` 换成固定序列
  并在每档开始前复位种子，否则比的是六段不同的行情。
- **别拿"首根收盘价"当跨周期的硬约束**：15 分钟档第 1 根收在 15 分钟处、30 分钟档第 1 根收在
  30 分钟处，是**不同的时刻**，本来就该不相等。能比的只有首**开**价，以及首根的**时间戳**。
  探针第一版拿首收做断言，误报过一次。
- **`gshot.py` 的 `--screenshot=` 必须给绝对路径**：相对路径 Chrome 会 rc=0 但 png 不落盘，
  看起来像"截了个空图"。

## 改成「预热 1 周 + 交易 1 个月」和七档周期时踩的坑

### 把指数重新定义成「当地天气的好坏程度」

用户的原话：「这个天气指数不妨描绘成当地天气的好坏程度，以此来修改参数以及模型写法」。
这句话点出的是**语义问题**，不是调参问题 —— 原来的指数**不表达任何东西**。

#### 改之前：天气只以「零中心异常度」进模型

```js
px = BASE + (tr - m)·TREND_K + (noise + carry + reg + dew + dish + micro + air + quake + typh + fcst)·amp
//           └─ 每一项都是 (x − 中位)/稳健标准差
```

所有天气项都是**对中位数的偏离**，也就是零中心的异常度。后果：

- 晴天和暴雨**都可能**是 `+2σ`，指数高低与天气好坏**完全无关**；
- 1000 不是"天气好"，只是"基准"；
- 实测 `corr(恶劣度, 指数) ≈ 0`。

#### 改之后：comfort 是基本面，价格围绕它波动

**① 新增 `comfort(mn, pm25) ∈ [0,100]`** —— 一个有绝对含义的标尺：

| 天气 | 平均 comfort（广州 92 天实测） |
|---|---|
| 晴 / 基本晴 | **81.5 / 81.4** |
| 阴 / 多云 | 79.9 / 79.9 |
| 毛毛雨 | 73~75 |
| 阵雨 | 64~66 |
| 雷暴 | **57.1** |
| 雷暴 + 冰雹 | **50.2** |

六个分量按"对体感的伤害程度"加权：体感温度 0.34、降水 0.21、天气码 0.20、
湿度（露点）0.15、空气 0.05、阵风 0.05。每项都是**连续分段线性**，不用硬阈值
（硬阈值会让指数在阈值附近抖）。分布 `min 38 / 中位 78.4 / max 97.3`。

**② `severity()` 重定义为 `−Δcomfort/10`** —— 天气变差则 severity 上升。
好处是价格模型里那些以 severity 为输入的项（噪声、跳变触发）语义不用重写。
**副作用是个惊喜**：`P.JUMP_AT = 1.8` 这一项**原来永久空转**
（真实天气 15 分钟内的 |Δsev| 极少超过 1.8），改完之后变成**每局约 9.6 次跳变** ——
README 里承诺的"每局出现几次连续暴跌"这才真的有了。

**③ 价格改成「基本面 + 双通道均值回归」**：

```js
anchor = BASE + (慢速comfort − 中位) × COMFORT_K     // 基本面：随天气缓慢移动
px     = px_prev + (anchor − px_prev)·REVERT          // 慢通道：钉住基本面
                 − noisePrev·NOISE_REVERT             // 快通道：噪声回 0
                 + shock
```

`cfSlow` 用**半衰期 12 小时的 EMA** 而不是即时 comfort：即时值的 `|Δ|` p99 是中位的
**61 倍**（单根雷暴砸一个大坑），直接当价格就是"平时不动、偶尔跳一下"的尖刺序列。
`cfMed` 把指数**居中到 BASE**，否则一段整体舒服的天气会让指数常年停在 1150。

> **双通道是标定出来的关键，值得单独记一笔。**
> 单通道（只有 `REVERT`）时，lag-1 自相关**锁死在 0.84~0.95** ——
> 27 组参数扫下来都一样，说明它不由参数决定。原因是数学上的：
> 每根只回归 `REVERT` 比例，就把「anchor − px」变成了一个**一阶低通滤波器**，
> 锚点那条慢信号被**原样搬进价格**。真实标的是围绕价值**高频抖动**，不是黏着价值走。
> 加上快通道后自相关降到 **0.40**。

标定结果（`tools/solve_comfort_model.js` 扫参，6 局平均）：

| 指标 | 真实靶子 | 改之前 | 改之后 |
|---|---|---|---|
| 中位 \|涨跌\| | 0.1848% | 0.5117% | **0.1827%** ✅ |
| lag-1 自相关 | ≈ 0.02 | 0.873 | **0.383**（原 0.84） |
| p90/中位 | 3.35 | 2.73 | 4.45 |
| p99/中位 | 8.30 | 6.29 | 17.27 |

最终参数：`COMFORT_K=8`、`REVERT=0.003`、`NOISE_AMP=1.4`、`NOISE_REVERT=0.8`。

#### 还没做好的两件事（如实记录）

1. **`corr(天气, 指数)` 仍然接近 0**。但这个读数是**有偏的**：探针拿**即时的
   15 分钟 severity** 去比**12 小时平滑的锚点**，两者时间尺度差两个数量级，
   样本内本来就解释不了。实测锚点本身**一天移动 34 点（3.4%）**、
   92 天范围 −93 ~ +134 点，基本面是活的。要正确验收得改成
   `corr(慢速 comfort, 指数)`，探针还没改。
2. **p90/中位 4.45、p99/中位 17.27 仍比真实的 3.35/8.30 厚**。这是从原模型继承下来的
   CTF（中心极限）问题：本模型 = 大量独立随机项叠加 → 厚腰薄尾；
   真实行情是薄腰厚尾。双通道回归把它从 p99 19.35 压到 17.27，但没解决。
   要真正对上得换成"平时几乎不动、偶发跳变"的生成机制，那是重写价格模型。



原来的模型是「一局 N 天，速度 = 每秒推进几根 K 线」。加了周期档位之后这个定义就崩了 ——
1 分钟档一天 1440 根、1 日档一天 1 根，同样「每秒 3 根」在两个档位上差 1440 倍。

所以速度的单位重新定成「**每真实秒推进多少分钟天气**」。这样：

- 一局固定 **37 天 = 53280 分钟天气**（预热 7 天 + 交易 30 天），跟周期无关；
- 同一档位的墙钟时长只跟速度有关；
- 换周期只是**换个放大镜看同一段天气**，不会让一局变长变短。

代价是低价档位（1 分 / 5 分）一局要 53280 根、1 日档只有 37 根，两个极端都得照顾。

> **这条不变量后来又被质疑过两次，值得记下来。**
> 用户说"长档位变化不够快"，我先后怀疑过：推进量算错、插值不对、重绘频率不够。
> 实际量下来推进式子一直是对的 —— `G.acc += (SPEEDS/barMin())/TICK_HZ`，
> `G.acc × barMin() = SPEEDS` 分钟/秒，**式子里没有档位**。
> 真正的毛病是别的：一开始 `TICK_HZ=10` 时粗档位每 tick 只走 0.003 格源样本，
> 要 3.3 个 tick 才跨一格，于是**连续几帧价格一个数都不变**（实测活跃帧只有 47%/74%）。
> 那是"卡顿"，不是"流速"。
>
> 判断"流速对不对"只需要问一句：**换个档位，天气时间走得一样快吗？**
> 一样快就对了。至于"一根 1 日线该花多少秒"，那是 `SPEEDS` 这个手感参数，
> 不该混进架构里讨论。
>
> ---
>
> ### 流速与重建频率是**两个**旋钮（最后才理清的一条）
>
> 用户最后说的是："**无论怎么调整时间流速，其都应该是 1s 变化四次**"。
> 这句话把之前所有混乱都解释清了 —— 我一直在把两件事混成一件：
>
> | 旋钮 | 管什么 | 改它的后果 |
> |---|---|---|
> | `SPEEDS` | 天气时间走多快 | 一局变长变短，**每秒变几次不变** |
> | `TICK_HZ` | 一秒重建几次画面 | 画面更细更顿，**一局时长不变** |
>
> 解耦靠推进量除以 `TICK_HZ`：
>
> ```js
> G.acc += (SPEEDS[speedIdx] / barMin()) / TICK_HZ;
> //        └─ G.acc × barMin() = SPEEDS 分钟/秒 —— 与 TICK_HZ 无关
> ```
>
> 所以 `u` 的推进速率 = `SPEEDS×60/barMin` 次/秒，TICK_HZ 只决定"多久采一次样"。
> 定 `TICK_HZ = 4`，就是"一秒变 4 次"，**与速度档无关**。
>
> **我在这上面连错四轮，错法值得记下来：**
>
> | 轮 | 我做的 | 错因 |
> |---|---|---|
> | 1 | `SPEEDS = 15`（一格 1 秒） | 按"1 秒一格"猜，没抓用户的数 |
> | 2 | 重排 `[7.5,15,30,60]` 但没改默认档 | 改了刻度，默认还是旧的 |
> | 3 | 反推 `SPEEDS = 75`（一格 5 次） | 这次对了数，但**还是绑在流速上** |
> | 4 | `TICK_HZ = 4` | ✅ 把"变几次"从流速里拆出来 |
>
> 教训：**用户给的是"变化频率"，我却一直在调"时间流速"。**
> 这两个量在原来的代码里是耦合的（推进量除以 TICK_HZ 同时定了两者），
> 所以怎么调流速都改不对频率 —— 必须先把它们拆开。
>
> 最终刻度（`TICK_HZ = 4`，全程 1 秒 4 次）：
>
> | 档 | SPEEDS | 一格 15 分钟 | 每次推进 | 1 日一根 | 一局 30 天 |
> |---|---|---|---|---|---|
> | 实时 | 15 | 1.00 s | 3.75 分钟（0.25 格） | 96.0 s | 48.0 min |
> | 慢 | 30 | 0.50 s | 7.50 分钟（0.50 格） | 48.0 s | 24.0 min |
> | **悠闲（默认）** | **60** | **0.25 s** | **15.0 分钟（1.00 格）** | **24.0 s** | **12.0 min** |
> | 正常 | 120 | 0.13 s | 30.0 分钟（2.00 格） | 12.0 s | 6.0 min |
> | 狂暴 | 240 | 0.06 s | 60.0 分钟（4.00 格） | 6.0 s | 3.0 min |
>
> 默认选 60，因为它让 `TICK_HZ=4` 时**每次更新正好推进一格** ——
> "一秒变 4 次"和"一格一变"在这一档上重合。
>
> ⚠ 4 Hz 有个必然代价：**一格里更新几次 × 一根里几格 = 一根几秒 × 4**，三者绑死。
> 所以 30 分以上的粗档位一次更新会跨好几格（1 时跨 16 格、1 日跨 96 格）。
> 想"一格一变"就得让一根走 96/4 = 24 秒 —— 这正是默认档在做的事。

> 预热后来按用户要求从 10 天缩到 **7 天（一周）**，交易段一个月不动。
> **只改 `WARM_DAYS` 这一个常量就够了** —— 预热段根数、交易段根数、源数据根数、
> 图表窗口全部是 `warmBars()` / `tradeBars()` / `totalBars()` / `srcBars()` 派生出来的，
> 没有一个地方硬编码天数。这就是当初把它们抽成函数的回报。

#### 这一轮改了什么

**混沌跳跃**（`CHAOS_P` / `CHAOS_K`）—— 肥尾的真正来源。
对账发现原来 max 只有 5.8%、峰度 5~13，尾巴完全是平的。查下来两条原因：
`JUMP_AT = 1.8` 的门槛比新 severity 的 p99（2.03）还高、**几乎不触发**；
而 `NOISE_REVERT = 0.8` 会把冲击立刻砍掉 80%。两者一起把尾巴压平了。

真市场的肥尾来自**流动性 / 杠杆级联**（强平砸盘 → 触发更多强平），和天气无关，
所以单开一条通道：`heat`（波动率聚集）+ `calm`（平静越久越容易爆发）
+ 幂律尾巴。它**不进快通道**（不被 `NOISE_REVERT` 回拉），否则尾巴又平了。

> ⚠ 这一项我调了两轮才对。第一版 `CHAOS_P=0.0035 × 倍率 5.4 = **1.89%** 触发率`
> —— 每局 **67 次**跳跃，跳跃变成了常态噪声；而 `tailv` 中位约 1.0 意味着
> "中位那次跳"只有 0.16%，于是**中位涨跌被抬到 0.1946%，尾巴反而没肥起来**。
> 肥尾要的是"绝大多数时候不跳，跳就跳大的"：`CHAOS_P` 降到每局 6~10 次，
> `tailv` 去掉那个 0.3 的底。改完峰度 13 → 38、max 5.8% → 8.5%。
>
> 另一个坑：`let heatEma = 0, prevPx = pxPrev;` 写在 `pxPrev` **前面**会踩 TDZ，
> 而 `pickSeries` 是被 `try` 包着的 —— 表现成"取不到序列"、五个城市全跳过，
> 完全看不出是这里。**初始化顺序也是逻辑。**

#### 架构改动：从「连续噪声 + 慢回归」换成「事件驱动 + 短记忆」

原架构的自相关**锁死在 0.38**，扫 27 组参数（`NOISE_AMP`/`REVERT`/`COMFORT_K`/
`NOISE_REVERT`）下限就是 0.35。原因不是没调对，是**数学上的必然**：

```
px = pxPrev + (anchor − pxPrev)·REVERT − noisePrev·NOISE_REVERT + shock
     ↑ 前景价格出现在等式右边 → 必然产生 AR(1) 记忆
```

只要回归慢（为了钉住基本面），滞后一阶相关就 ≈ 1−REVERT，**降不下来**。
「慢回归」和「低自相关」在这个式子里不可兼得。

真实市场不是连续信号，是**事件驱动**的：一笔成交到达 → 一次价格冲击 →
按**韧性**快速衰减 → 下一笔再来。所以新架构把价格**定义**成两个互不依赖的状态之和：

```js
impactState = impactState·(1 − INERTIA) + evSum;   // 冲击累加，快速衰减
px          = anchor + impactState;                // 前景价格**不再出现在右边**
```

关键在**衰减速率与到达速率的关系**：衰减慢于到达 → 冲击首尾相接 → 又是 AR(1)；
衰减快于到达 → 每笔基本独立 → 自相关下得来。

顺带落地的两个真市场特征：
- **波动聚集**：到达率**自激** —— 来得多则下一根到达率更高（`flow` → `arrival`）。
- **肥尾**：单笔冲击用幂律尾巴。p90/中位、p99/中位、max 三项**一次对上**：

| 指标 | 真实 BTC / WIF | 连续噪声架构 | 事件驱动架构 |
|---|---|---|---|
| p90/中位 | 3.50 / 3.25 | 4.2 | **3.95** |
| p99/中位 | 8.76 / 7.69 | 15.6 | **8.6** ✅ |
| max 单根 | 4.2% / 38% | 8.5% | **26%** ✅ |

新参数：`INERTIA`（衰减）`FLOW_RATE`（到达率）`EVENT_K`（单笔幅度）`FLOW_DECAY`（自激记忆）。
`REVERT` / `NOISE_REVERT` 已废弃删除。

### 一局的天数要跟「速度」解耦

### 光标停在预热段最后一根，不是第 0 根

`resetState()` 里 `G.i = 0` 要改成 `G.i = warmBars() - 1`。写成 `warmBars()` 也行，
但那样第一帧就有一根「未来」K 线被算进收益曲线。**用 `- 1`，`G.i` 始终指向"最后一根已经走完的 K 线"**
这个不变量后面到处都依赖（`processOrders`、`render`、`setBar` 全是按这个假设写的）。

### 顶栏进度要按交易段算

`G.i + 1` 现在是「含预热的总根数」。直接显示会变成 `已交易 932 / 2880 根`，
前 672 根是白送的。正确的是：

```js
const done = Math.max(0, Math.min(tradeBars(), G.i + 1 - warmBars()));
```

### `visBars()` 也得从 `roundBars()` 换成 `totalBars()`

`visBars()` 决定图表能显示多少根。它原来等于「一局根数」，现在一局有 37 天，
如果还按 `roundBars()`（只有 30 天）算，切到 1 日档时**预热段的 7 根日 K 会被裁掉**，
跟「一进来就有 1 周历史」直接矛盾。

### 双 grid 的 series 必须显式声明轴

ECharts 加了第二个 grid（成交量副图）之后，`xAxisIndex` / `yAxisIndex` 默认会按 series
顺序去猜。蜡烛、MA、大盘三条都得**显式写 `xAxisIndex: 0, yAxisIndex: 0`**，
量柱写 `xAxisIndex: 1, yAxisIndex: 1`。不写的话有 series 会挂到副图的轴上，
表现是「主图上多出一条看不懂的线」或者「蜡烛跑到副图里」。

### `trigger: 'axis'` 的 tooltip 不能用 `p[0]`

两个 grid 共用一个 tooltip 之后，鼠标在主图上时会同时命中
`{gridIndex:0, ...}` 和 `{gridIndex:1, ...}` 两个数组元素，顺序不保证。
`p[0]` 有一半概率拿到量柱那一项（它的 `data` 是个数字，不是 OHLC 对象），
于是 tooltip 全是 `undefined`。正确写法是按名字找：

```js
const it = (p && (p.find(x => x.seriesName === 'WXI') || p[0]));
```

### 「像股市」是个可以用数字量的目标

原来的快分量 `(sev - trend)` 每一项之间几乎独立，画出来到处跳空。
量了一下 **lag-1 自相关 = 0.031** —— 那就是「独立随机点」的特征值。

给快分量叠一层 EMA（`NOISE_A = 0.45`）之后自相关到 **0.208**，落在真实股票分钟级
（0.1 ~ 0.4）的区间里。两个坑：

- **EMA 会吃掉方差**，所以必须配一个 `NOISE_BOOST = 1.42` 把幅度补回来，
  否则整局振幅会从 35% 掉到 20% 出头，"难度"被顺手改掉了。实测补完之后
  单根涨跌中位 0.261% -> 0.301%，几乎没动。
- **A/B 必须钉住 `Math.random`**。`pickSeries` 里的窗口偏置用 `Math.random` 挑起点，
  不换成固定序列的话比的是**两段完全不同的行情**，结论毫无意义。
  `tmp/b2-old.txt` 里存了改之前那一版的结果。

### 1 日档的影线会非常大，但那是真的

一天 96 根聚合成 1 根时，`high` / `low` 取的是**整天 96 根的极值**。
天气里一次对流爆发能让指数在一小时内窜 200 点，于是日 K 上就是一柱冲天的上影线。
第一眼看像 bug，其实是**正确聚合**的结果 —— 真实日 K 遇到盘中插针也是这样。
想去掉只能砍掉 `JUMP` 冲击，那是拿真实感换好看，不值。

### 顺手记两个小坑

- `#ggBar button` 的 `flex-basis` 要从 `calc(33.333% - 3px)` 改成 `calc(25% - 3px)`
  —— 七档按 33% 排会变成 3 + 3 + 1，最后一档孤零零占一行。
- 档位名带空格的（`1 分` / `1 时`）在 `data-bar` 上要留英文数字下标（`data-bar="0"`），
  别拿文案当键；`syncBar()` 用 `U.$$('#ggBar button')` 而不是类名选择器
  （那几个按钮**没写类**，用 `.gg-bbtn` 会一个都选不中）。

## 两处「滚不动」：雷达的省份行和预警列表

群里反馈的两个问题，根因完全不同，但表现都是"这一块卡住了"。

### 雷达 / 云图那几排按钮：藏了滚动条 = 桌面端真的滚不动

`.wx-seg` 本来就是 `overflow-x:auto`，8 个雷达大区按钮在窄屏上放不下也确实能滚 ——
**但滚动条被 `scrollbar-width:none` + `::-webkit-scrollbar{display:none}` 藏掉了**。
在触屏上手指一划就滚，所以移动端测试完全正常；桌面端就废了：鼠标滚轮默认只滚垂直方向，
横向又没有可见的滚动条可以拖，用户看到的就是"这一排按钮滚不动"。

修法两条一起上：

1. **把滚动条留出来**，收成 6px 的细条（`.wx-seg::-webkit-scrollbar{height:6px}`），
   给一个"这里能滚"的视觉提示；
2. **给滚轮挂一个转横向的处理器**：

   ```js
   document.addEventListener('wheel', e => {
     const seg = e.target.closest && e.target.closest('.wx-seg');
     if (!seg || seg.scrollWidth <= seg.clientWidth + 1) return;  // 没得滚就别抢事件
     const d = Math.abs(e.deltaY) > Math.abs(e.deltaX) ? e.deltaY : e.deltaX;
     const before = seg.scrollLeft;
     seg.scrollLeft = before + d;
     if (seg.scrollLeft !== before) e.preventDefault();  // 滚到头就把事件还给页面
   }, { passive: false });
   ```

   两个细节：**必须 `passive: false`**（否则 `preventDefault()` 无效，页面会跟着一起滚）；
   **滚到头要主动放行**（不 `preventDefault`），不然鼠标停在这排按钮上时整页滚不下去。
   事件委托绑在 `document` 上 —— 这些行是 `innerHTML` 重画出来的，绑不到具体元素。

### 预警列表：flex 子项忘了 `min-height:0`

`.wx-body` 是 `overflow:hidden` 的 flex 列，里面塞一个长列表就必须让列表自己滚。
第一版只写了 `overflow-y:auto`，结果完全不滚 —— 因为 **flex 子项的 `min-height` 默认是 `auto`**，
内容是 20 条预警时它就把自己撑到 2040px，父级一裁，`overflow-y:auto` 根本没有可滚的区间
（`scrollHeight == clientHeight`）。

正确的三件套：

```css
.wx-warn{flex:1 1 auto; min-height:0; overflow-y:auto;}
```

顺带把条目加了 `flex:none`，不然它们会被 flex 压扁。

**怎么验的**（`web/__sc.html` 探针，跑完删掉了）：量 `.wx-warn` 的
`scrollHeight`（2040）与 `clientHeight`（740），再把 `scrollTop` 设成 99999 看它有没有真的落到 1300。
只量 CSS 属性没用 —— `overflow-y:auto` 在滚不动的时候看起来也一样。

> 无头环境里雷达取不到图（气象局那个时段没发布），三层按钮根本不会渲染，
> 所以那一条是**手工塞了一段和 `playerHTML` 一样的 `.wx-segs` 结构**来验的：
> 25 个省那行 `scrollWidth=1656 > clientWidth=1078`，`scrollLeft` 能推到 578；
> 派发 `wheel(deltaY=120)` 后 `scrollLeft` 从 0 变 120、`defaultPrevented=true`。

### 预警按距离排序

`weather.js` 的 `warnings()` 本来就取回了 `lat` / `lon`（气象局的 warning 接口带经纬度），
所以排序不用额外请求 —— 拿当前城市的坐标算大圆距离，升序排，再把距离标在时间那行右边。
排不了（没选城市 / 某条没坐标）就退回原来的顺序，不显示距离，**绝不编一个距离出来**。

## 未收盘那根 K 线（live bar）

用户的原话是「类似于真实交易所里的那个 k 线动画，比如在日 k 线时，没那么快更新到下一个 k 线，
所以那个 k 线是根据内部变化来在页面上也实时变化的」。原来的实现是**冻住的**：
`tick()` 只在攒够一整根时才把现价设成新一根的收盘价，没攒够直接 `return`（连 `render()` 都不调），
而 `drawCharts()` 只画到 `G.i + 1`。于是一根越粗冻得越久 —— 1 日档 + 正常速度是
`1440/45 = 32 秒`完全静止，4 时档 5.3 秒。

### 形状交给真实数据，不要加"摆动参数"

第一版方案里我打算加一个 `LIVE_W` 系数，用 `sin` 造一点盘中摆动，还准备好了三个档位
（温和 0.15 / 活泼 0.35 / 纯平滑 0）。用户直接否了：**「这个不是根据实际情况确定的吗，
我们暂时不要瞎改」**。这句话是对的，而且指出了更好的解法：

`minutely_15` 是数据源的真实粒度，而 `pickSeries` 已经把那一份**原样 15 分钟序列**留在
`G.base` 里了（3552 根）。所以盘中怎么走不该是编的，应该是**光标沿真实样本往前走**：

```js
dpb  = barMin / 15                       // 一根 K 线 = 几根 15 分钟源
起点 = G.i * dpb + dpb - 1               // 上一根的收盘那根源数据
终点 = (G.i + 2) * dpb - 1               // 本根的收盘那根源数据
光标 = 起点 + u * (终点 - 起点)           // u = G.acc ∈ [0,1]
```

这样"一根 K 线里穿过多少根真观测"完全是算出来的，不是我给的系数：

| 档位 | dpb | 探针实测盘中穿过的真采样数 |
| --- | --- | --- |
| 1 分 / 5 分 | 0.067 / 0.33 | **0** —— 比数据源更细，子 K 线内部没有源样本（见下面那条补记） |
| 15 分 | 1 | 2 |
| 30 分 / 1 时 / 4 时 | 2 / 4 / 16 | 3 / 5 / 17 |
| 1 日 | 96 | **97** |

上下影线也照这个口径：取**已经走到的那几根真样本的真实极值**，不按比例摊。
只有父层（`base[s0]` 那 15 分钟内部）的极值需要按"已走完的比例" `pr` 继承 ——
它本身含 `WICK_K = 0.30` 的建模影线，这样收盘时才 100% 用上。

### `srcF` 这个式子被探针逮了两次

两版都错，而且**都是 `tools/test_live_wick.js` 当场挂断言才发现的**（肉眼看图看不出来）：

| 版本 | 写法 | 症状 |
| --- | --- | --- |
| ① | `srcF = (G.i + u) * dpb` | u=0 落在上一根的**开盘**上（不是收盘），端点差一根 |
| ② | `srcF = G.i*dpb + (u*dpb + dpb - 1)/dpb` | 把绝对位置补上了，但那个偏移**没乘 dpb** —— 整根走完光标只前进 **1 根源数据**。4 时档一根跨 16 根样本，盘中却只穿过 2 根（`seen={320,321}`），1 日档同样只有 2 根 |
| ③ | `起点 + u*(终点-起点)` | 对 `dpb > 1` 和 `dpb < 1` 都自动成立 |

教训：**"起点 + u × 偏移"这种写法里，偏移必须是（终点 − 起点），不能是凭直觉拼的一个表达式** ——
后者在 dpb=1 时看着完全正常，换个档位就错，属于"只在小档位上验过"的典型。

### `G.liveOpen` 那个字段是个时序坑

一开始为了让 live bar 的开盘价跟左边那根接上，加了个 `G.liveOpen` 字段，在 `tick()` 里赋值。
问题是 `liveAt()` 在半根分支里**先被调用**，那时 `liveOpen` 还是**上一根周期的陈值** ——
4 时档那根蜡烛的开盘价直接少了 7.7 点（1027.205 vs 1034.935），low 跟着一起错。

删掉字段就好了：**live bar 的开盘价在定义上就是"上一根收在哪儿"**，直接读
`G.series[G.i].c` 即可，不需要任何额外的状态。教训：能从已有状态推出来的东西
不要另存一份，存了就有同步问题。

### 收盘瞬间必须零跳变

这是整套算法唯一不可妥协的性质：`u` 走到 1 时光标正好落在 `(G.i+2)*dpb - 1` 这个**整数**上，
于是 `kf = 0`、`c` 精确等于那根真 K 线的收盘价，高/低也精确等于它。
探针里这条是硬断言（五档 × `u=1` 与 `resample` 真值逐项相等，误差 < 1e-9）。
如果这里差一点点，"live bar 变成真 K 线"的那一帧就会看见蜡烛跳一下。

### ⚠ 补记：1 分 / 5 分这两档当时**并没有**满足上面那条

上面那句"五档"是实话，也是问题所在 —— **验的档位里就没有 dpb < 1 的两档**。
后来合并进来的 fork（PR #1，`wuzhang114`）里 `liveAt()` 被重写过，我独立复验时逐档量了一遍，
1 分 / 5 分是坏的：

| 档 | `cFill` 恰好 == `series[j-1].c` | 画出来的收盘 vs 真 K 线 |
| --- | --- | --- |
| 1 分 | 3733 / 3999 | 不符 3720/3999，中位差 0.04%，最大 3.74% |
| 5 分 | 2666 / 3999 | 不符 2665/3999，中位差 0.03%，最大 3.65% |
| 15 分及更粗 | 0 | **0 不符** |

根因就在同一个公式上：`lastOf(j) = ceil((j+1)·dpb) - 1` 在 `dpb < 1` 时，
**同一根父 K 线的相邻子根取值相同**（一根 15 分钟源样本被 15 根 1 分钟子 K 线共用）。
于是 `start === end`：

```js
const bLo = start + 1, bHi = endI;                          // bLo = bHi + 1，区间是空的
const cur  = Math.min(bHi, Math.floor(srcF + 1e-9));         // = start
const c    = (cur >= bLo && cur <= bHi) ? G.base[cur].c : o; // 判据恒假 → cFill 永远是 o
```

`cFill` 退化成 `o`（上一根子根的收盘），而且 `srcF` 停在整数上，
`kf = srcF - floor(srcF)` 恒为 0 —— 画图价一整根纹丝不动，到 `u=1` 才猛地一跳。
**"光标沿真实样本走"这套前提在比数据源更细的档位上根本不成立：子 K 线内部没有源样本可走。**

改法：`dpb < 1` 直接单独走一条分支，目标改成**本根自己**（`G.series[G.i]` 就是那根子 K 线），
从开盘价 `o` 按完成度 `u` 线性走过去：

```js
if (dpb < 1) {
  const nb = G.series[G.i] || {};
  const cT = nb.c, hT = nb.h, lT = nb.l;
  const cD = o + (cT - o) * u, hD = o + (hT - o) * u, lD = o + (lT - o) * u;
  return { t: tgt.t, o: o, h: Math.max(hD, o, cD), l: Math.min(lD, o, cD),
           c: cD, cFill: (u >= 1) ? cT : o, i: G.i + 1, u: u, s0: G.i };
}
```

能这么写是因为 `resample` 展开时恒有 `series[G.i].o === o`、
`series[G.i].h ≥ max(o, c)`、`series[G.i].l ≤ min(o, c)`（见 `resample` 里的
`h: Math.max(o, c) + wk` / `l: Math.min(o, c) - wk`），所以线性插值途中
**"极值包住实体"始终成立、`h` 只增 `l` 只减**，`u=0` 仍退化成一个点，`u=1` 精确落到真 K 线。

修完实测（北京，base 3552 根，七档全量）：

| 断言 | 1 分 | 5 分 | 15 分 | 30 分 | 1 时 | 4 时 | 1 日 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `u=1` 的 `o/h/l/c` 等于 `series[j]` | 0/3999 | 0/3999 | 0/3550 | 0/1774 | 0/886 | 0/220 | 0/35 |
| `u=0` 是一个点 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 极值包住实体 / `h`只增`l`只减 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

偏差全部是 `0.00e+0`，也就是**逐位相等**；15 分及以上的老路径一个字节没动（分支是提前 return 的）。

教训和上面那条一样，只是更狠一点：**"全档位"这句话必须真的把 `dpb < 1` 也数进去**。
`dpb = 1` 是一道门槛：门槛这边光标在源样本之间走，门槛那边光标在**编出来的**子 K 线之间走，
两边的公式不可能共用。

### ECharts 的 option 合并：**数组是整体替换的**

局部重绘（`liveTick()`，10 Hz）必须用合并模式 —— 传 `notMerge = true` 就只认那一小份
option，横轴类别、均线、大盘线、dataZoom 全被清掉。但合并模式有个必须知道的行为：

```js
C = function (t, e, n) { ... !q(o) || !q(r) || Y(o) || Y(r) || ... ? (!n && i in t || (t[i] = T(e[i]))) : C(r, o, n) }
```

`Y` 是 `isArray`。所以 `data` 这种数组字段命中 `Y(o)` 那条分支 → **`t[i] = T(e[i])`
把整个数组替换掉**，不是逐元素合并。我第一版就是想"只传最后一根蜡烛"，
那会把 90 根蜡烛全删了。现在 `drawCharts()` 和 `liveTick()` 共用同一个 `liveNote()`
来造完整数组，两边口径不可能漂。

顺带：`liveTick` 用 `setOption(opt, false, true)` —— 第三个参数 `lazyUpdate` 让 ECharts
把这次改动合并到下一帧再画，避免 10 Hz 的同步 flush。

### 成交改成按盘中价（所见即所得）

以前在收盘前下单，成交价是"你屏幕上还看不到的那根的收盘价"。现在 `G.price` 就是盘中的
live 价，所以市价单、挂单、止损止盈全按它成交，账户权益 / 浮动盈亏 / 爆仓距离也跟着逐帧动。
**爆仓因此变成按盘中价触发** —— 更接近真实强平，代价是止损被"盘中插针"扫掉的概率变高。
这是用户明确选的（三个选项里选了"所见即所得"）。

一个必须保留的顺序：`processOrders()` 的判定区间仍然是「上一根收盘 → 本根收盘 + 本根影线」，
不能用那个只走到一半的盘中价 —— 否则止损永远只在收盘后才可能被扫到，
"影线扫止损"就模拟不出来了。

### 怎么验的（`tools/test_live_wick.js`，127 项断言）

不需要浏览器、不联网：`game.js` 是个 IIFE、只把 `Game` 挂到 window 上，内部碰 DOM 的地方
全走 `$() = document.querySelector`，所以给一个"什么元素都能造出来"的假 `document`，
价格模型和 live bar 的数学就能在 node 里单独跑。**验的是真代码，不是把公式抄一遍。**

> **这个文件是"先写测试再改代码"的产物，也是这一轮没再走弯路的直接原因。**
> 在那之前我是靠肉眼看盘面判断对错的 —— 结果同一个影线 bug 反复改坏二十次都发现不了，
> 每次都以为修好了。

现在的断言分五组，跑**全档位 × 多个 `G.i`**：

1. `u=0` 退化成一个点（`h = l = c = o`）
2. **极值 `h`/`l` 单调** —— ⚠ 这里我一开始测错了：测的是「影线宽度单调」，
   但蜡烛收在最高处时上影本来就该是 0。**真正必须单调的是极值本身**
   （价格回头不能取消已触及的极值）。优化了一个错误的指标好几轮。
3. `u=1` 逐位等于真 K 线（`h`/`l`/`c` 三项都比，比宽度更本质）
4. **乱序/重复推进幂等** —— 状态机必须只依赖当前状态。
   这条是为了防一类特定的错：中途用跨帧累加器时，探针在同一个 `u` 上反复调用
   会重复累加，`liveAt()` 就不再是纯函数（实测把通过数从 48 打回 37）。
5. 全 7 档 × `u∈[0,1]` 的有界性与有限性（`l ≤ min(o,c) ≤ max(o,c) ≤ h`）

**必须跑全档位**，这是踩出来的：`b0i`（本根第一个源样本）我先后写错过三次 ——
`G.i*dpb+dpb`（小数档错）、`G.i+1`（dpb≥2 错）、`floor(G.i*dpb)+1`（dpb=1 时循环空转）。
**每次都是只在一个档位上验过就以为对了。**

## 用真实交易所数据标定操盘手的系数

用户的要求是：「去欧易等平台下载真实操盘数据，学习一下如何调参或者改变公式来接近真实的数据变动，
大城市像主流货币，小城市像盗版币」。

### 数据怎么来的

`tools/fetch_crypto.py` —— 欧易（OKX）**公开**行情接口 `/api/v5/market/history-candles`：
免 key、免账号、不登录、不碰任何交易接口。9 个对 × 365 天 × 15 分钟 = 每对 35100 根（约 20 MB）。

选出 9 个对是照"流动性从大到小"排的，这个顺序就是映射到城市大小的依据：
`BTC / ETH`（主流）→ `SOL / DOGE`（人气）→ `SUI / APT`（二三线）→ `PEPE / WIF / BONK`（模因）。

三个必须先知道的坑：

1. **单页最多 300 根**。`limit` 给 400/1000 也只回 300（实测）。
2. **默认 User-Agent 会被 403**。`Python-urllib/3.8` → 403，Chrome UA → 200。
3. **本机直连解析不了 `www.okx.com`**（`getaddrinfo` 直接失败），必须走系统代理
   （注册表里的 `127.0.0.1:7897`）。PowerShell 的 `Invoke-WebRequest` 会自动读那个设置，
   **Python 不会** —— 报错是 `URLError: [Errno 11004] getaddrinfo failed`，看着像网络不通，
   其实是没走代理。而且 `urllib` 的 `ProxyHandler` 在这台机器上也不生效，
   只有进程级环境变量可靠。设完之后仓库原有五个源照样通，代理是只加不减。

### 量出来的真实基准（这才是靶子）

```
BTC  单根|涨跌| 中位 0.0822%   p90 0.2681%   p99 0.6178%   自相关 +0.022
SOL                0.1577%       0.5330%       1.3220%            -0.010
WIF                0.2541%       0.8249%       1.9544%            -0.019
```

三个可以直接用的结论：

- **城市梯度 = 3.09×**（BTC → WIF）。这是"大城市像主流币、小城市像山寨币"的**量化目标**，
  以前只能拍，现在能量。
- **自相关 ≈ 0**。真实 15 分钟几乎没有记忆（9 个对全在 ±0.05 内）。
  仓库原来拿 0.208 当卖点（"一段一段地推"）—— 那个数是拿"真实股票分钟级 0.1~0.4"
  当参照定的，**加密 15 分钟并不符合那个参照**。
- **波动率是 √t 标度，不是线性**。真实 15m/1m 单根波动比 = 3.63×，而 √15 = 3.87×。
  而游戏里 1 分档是**线性**摊成 15 根的（一根摊成 15 根），单根波动会被压到 1/15
  而不是 1/3.87 —— **小了约 4 倍**。这条直接否掉了"1 分/5 分档按线性插值展开"的做法。

### 改了什么（两处）

**① `cityWeight()` 重写 —— 这是梯度的唯一载体，而它原来是坏的**

| | 改之前 | 改之后 |
| --- | --- | --- |
| 直辖市 | 4 城 3.0 | 4 城 3.0 |
| 省会 | **3 城** 2.2 | **27 城** 2.2 |
| 有国家站的地级市 | 305 城 1.6 | 305 城 1.6 |
| 有 path 的市 | **0 城**（死代码） | — 已删 |
| 区县 | 40 城 0.6 | 40 城 0.6 |

两个坑：认省会用的是「市名以省名开头」（`nm.startsWith(core)`）——"广州"不以"广东"开头、
"杭州"不以"浙江"开头，实测**只命中 3 城**，于是 305 座城权重完全相同、梯度形同不存在。
另外还挂着 `if (c.path) return 1.2`，而 `cities.json` 里**每座城都有 path**，那一档永远走不到
（README 里"有 path 的 1.2"就是它）。现在省会名单写死在 `CAPITALS` 里。

**② 新增 `cityAmp()`，把城市权重乘到所有随机项上**

这才是"主流币 ↔ 山寨币"的落点。旧模型里**只有 `dish` 一项**受城市影响，
而 `dish` 只占波动方差的约 4% —— `noise`(36%)、`carry`(49%)、`micro` 全与城市无关，
实测梯度因此被稀释成 **1.78×**（目标 3.09×）。
现在 `noise / carry / reg / dew / dish / micro / air / quake / typh / fcst` **全部**乘 `cityAmp`，
**趋势项不乘** —— 趋势是真实天气过程本身，所有城市面对同一场对流，
差别该体现在"盘面反应"而不是"天气不同"。这也正是"小地方更容易被推着走"的物理含义。

### 标定结果（诚实版）

| 指标 | 真实 | 改之前 | 改之后 |
| --- | --- | --- | --- |
| 波动水平（中位） | 0.1848% | 0.4211% | **0.1753%** ✅ |
| 城市梯度 | 3.09× | 1.78× | **3.66×** ✅ |
| 逐档对照 | — | — | 直辖市 0.120%（BTC 0.099）／省会 0.142%（ETH 0.130）／地级市 0.175%（SOL 0.158） |
| 自相关 | ≈0.02 | 0.20 | 0.43 ❌ **反而更远了** |
| p90/中位 | 3.35 | 2.82 | 4.45 ❌ |
| p99/中位 | 8.30 | 18.29 | 11.24 ⚠️ 近了但没到 |

**水平与梯度已经达标，形状与自相关没有。** 而且不是没调到，是**结构性做不到**：

- 本模型的价格 = 十几个独立随机项叠加 → 中心极限定理把分布推向**厚腰薄尾**；
  真实行情是反过来的**薄腰厚尾**（长时间极静 + 偶发暴动）。要真正对上，
  得把生成机制换成"平时几乎不动、偶发跳变"，那是重写价格模型，不是调参。
- **自相关更是被结构锁死的**。价格 = 趋势项（ρ1 = 0.921，极平滑）+ 随机项（ρ1 ≈ 0.17）。
  想整体 ρ1 接近 0 就得把趋势压到 2% 方差占比（`TREND_K ≈ 2`），那时趋势在图上几乎看不见 ——
  而"骑趋势"是玩法本身。**保玩法就要接受 ρ1 偏高。**
- 还有一条**梯度上限**：趋势项是所有城市共用的，它占的方差比例越高，大小城市差别越被抹平。
  实测要拿到 2.5× 以上的梯度，趋势的方差占比就不能超过约 14%。这也是 `TREND_K`
  从 50 降到 8 的原因。

### 顺带发现的两件事

**`JUMP_AT` 基本是空转的。** 实测把它从 1.8 往上调，结果**一模一样** ——
说明真实天气在 15 分钟内的 `|Δsev|` 极少超过 1.8，那个"突然拉到底"的冲击机制
在当前参数下几乎不触发。README 里描述的"每局出现几次连续 3 根跌 8~15% 的段"
需要重新验证（`JUMP_AT` 现在定在 1.8）。

**测量方法本身踩了三个坑**，每一个都会得出错误结论：

1. **用 `(c[i]-c[i-1])/c[i-1]` 算游戏涨跌幅是错的**。指数在 1000 附近、单根只动 0.02%，
   也就是第 15 位有效数字 —— 双精度下差值会被舍入吃掉，剩下的**全是浮点噪声**，
   而白噪声的 lag-1 自相关恒为约 −0.5。于是量出一个漂亮的 −0.5，看着像"行情在锯齿翻转"，
   其实是我的测量坏了（真实值 +0.185）。改成 `diff/prev`（分子是精确可表示的差值）。
2. **导出游戏序列时按时间排序是错的**。每局是同一段 92 天里**随机截的重叠窗口**，
   排序会把 8 条价格曲线交错混在一起，相邻两根来自不同窗口 → 又是一堆假跳变。
   正确做法是保持每局内部顺序、局与局之间**不跨着算涨跌**（导出时记 `bounds`）。
3. **自相关必须逐城市各算各的再平均**，把三个城市的序列拼成一条再算的话，
   拼接处同样是假跳变（实测拼着 0.505 / 分开 0.445），搜索会因此选错参数。

教训是同一个：**任何"把不同来源的序列首尾相接"再统计的做法，都会在接缝处产生假跳变，
而假跳变几乎总是表现为强负自相关。** 看到 ρ1 ≈ −0.5 就该先怀疑接缝，而不是怀疑模型。

## 存档 + 离线追赶 + 安卓竖屏：三个坑

这一轮改了三件事：游戏面板改名（`Climate Create Bet`）、中途退出不清进度、安卓竖屏同时看图和操作。
记三个真的会再踩的坑。

### 一、存档要存 `base`，不能存 `series`

一局 15 分钟基准是 3552 根，但 1 分钟档的 `series` 是**插值展开**出来的 **53280 根**。
`localStorage` 配额约 5 MB，存 `series` 会直接撑爆（而且写失败不一定抛异常，可能静默丢）。
`base`（15 分钟原样序列，约 525 KB）与周期无关，恢复时 `resample(base, baseSeeds, baseReg)`
重采样一遍就回来了 —— **和局中换周期走的是同一条路**，不用新写一份重建逻辑。

存档字段里 `barIdx` / `speedIdx` 必须做范围校验再赋给 `G`：
用户可能在旧版本存过 10 档速度的游戏，回来时 `SPEEDS[save.speedIdx]` 是 `undefined`，
`undefined` 参与算术会变成 `NaN`，而 `NaN` 会一路安静地传到权益里。

### 二、离线追赶必须复用 `stepBars()`，不能另写一条"快进"

最省事的做法是直接把 `G.i` 往前挪几十根、刷新一下权益。**那是错的** ——
挂单成交、止损止盈、滑点、手续费、爆仓判定、天气日历新闻全都发生在"逐根推进"里面，
跳过去等于**离线期间事件一律不触发**，玩家回来会发现"挂了限价单，价格明明走过去了却没成交"。

正确做法是把 `tick()` 里的逐根循环抽成 `stepBars(step, silent)`，在线走它、离线补推也走它，
只是 `silent = true` 时跳过 `floatText` / `beep` / `vibrate` / `render()`（补 480 根时
每根都重绘一次图表会卡死）。补推完再 `render()` 一次。

`silent` 只压**表现层**，不压**逻辑层**：爆仓照样爆、结算照样结算。
所以"离开 40 小时"回来看到的是**已经爆仓的结算页**，这是刻意的。

### 三、`position: sticky` 干不了"下单键常驻底部"

安卓竖屏要"主图钉在顶部 + 控件区滚动 + 下单键常驻底部"。第一版给 `.gg-btns` 写
`position: sticky; bottom: 0`，探针一量：滚到底时按钮跑到 **y = 15**，也就是被滚走了。

原因：sticky 只在**它的包含块内部**粘。`.gg-btns` 的父级是 `.gg-trade`，只包"下单区"那一小段，
滚出 `.gg-trade` 的盒子之后 sticky 就没有约束了，跟着一起滚。
换成 `position: fixed` 才对。

选择器还必须写 **`.gg-trade > .gg-btns`** 而不是 `.gg-btns`：
封面卡里那对「开始操盘 / 算了」也带 `.gg-btns` 类（`.gg-card .gg-btns`），
不限定父级的话它们也会被钉到屏幕底部去。

### 附带：两个探针工具自身的坑

- **`--screenshot=` 必须给绝对路径。** 给相对路径（`tmp\m2.png`）时 Chrome `rc=0` 但**不落盘**，
  `os.path.exists()` 是 `False` —— 看起来像"启动了但没截图"，其实是被当成了别的路径。
- **每次跑用一个新的 `--user-data-dir`。** 共用一个目录时，上一轮被 kill 掉的 Chrome
  会留下锁文件，下一轮 Chrome 会**静默退出**（`rc=0`）而不落盘。
  （这条和"必须绝对路径"叠在一起时特别难查：连续两次失败看起来完全一样。）
- Windows 上 Chrome 窗口有约 **500 px 的最小宽度**，`--window-size=390,844` 会被顶到约 500×692；
  `--force-device-scale-factor=2` 也**不会**把 CSS 视口除半（实测 780×1688 + DSF=2 → 视口仍是 762×1536）。
  所以这台机器上能测到的最小宽度就是 **500 CSS px**。

## 卡片、存档、"人机味"：一轮里踩的四个坑

这一轮改的是：竖屏卡片被常驻下单键压住、点「结束本局」后存档又长回来、提示文案改正式、
术语表补「主图上的几条线」、游戏里加「新手入门」。前两件都是真 bug，值得记下来。

> **先说清"文案改正式"改的是哪一半。** 游戏里的文字其实是两类，用户抱怨"人机味太重"的只是其中一类：
>
> | | 例子 | 该长什么样 |
> |---|---|---|
> | **流程性提示** | 退出确认、继续上局、补线提示 | 一眼看懂，别抖机灵。第一次玩的人要靠它决定按哪个键 |
> | **结算评语** | 「见好就收，也是一种本事。」「天台今天风很大。」 | 说给玩家听的，一本正经反而没意思 |
>
> 第一版我**把两类一起改成了陈述句**，结算卡变成了「本局使用了 20 倍杠杆并满仓，权益对反向
> 波动极为敏感」—— 准确，但没人想看这个。用户后来说「结算评语写得有趣有梗一点倒是没什么啦」，
> 指的就是这个。**一个"看起来不专业"的评价，不一定指向全部文字**，先分清是哪一类再动手。

### 一、`close()` 会把刚清掉的存档写回去

原来的退出流程是：

```js
// exitFlow() 里点「结束本局」
clearSave();
close();          // ← close() 第一句是：if (G.running && !G.ended) saveRound();
```

`clearSave()` 刚把 `tjs.wxgame_save` 删掉，`close()` 立刻判断"这一局还在跑"，
于是 `saveRound()` 又原样写了一份。下次进来照样弹「有一局尚未结束」。

**它是平台无关的** —— 电脑和手机都在，因为问题出在调用顺序上，不是出在存储上。
修法是把状态先改掉再删：

```js
G.running = false;   // 先让 close() 认为"没在跑"
clearSave();
close();
```

**教训**：一个"顺手保存"的钩子挂在公共出口（`close()`）上时，所有想绕过它的路径
都得**先把状态改掉**，光清存储是没用的 —— 钩子读的是状态，不是存储。
这类 bug 探针很好抓：`clearSave()` 之后调一次 `loadSaved()`，看是不是 `null`。

### 二、`position: fixed` 的下单键会压住卡片

上一轮为了"一边看图一边下单"，把 `.gg-trade > .gg-btns` 钉在屏幕最底部。
但开场说明、新手入门、结算卡、退出确认**也画在同一个 `#game` 遮罩里**，
于是卡片的按钮和那排常驻键叠在一起，谁在上面只看 z-index。

修法是给遮罩加一个状态类，卡片出现时让常驻键让位：

```css
.game-mask.cover-on .gg-trade > .gg-btns { display: none; }
```

```js
function showCover(html) { cover.innerHTML = html; cover.hidden = false; mask.classList.add('cover-on'); }
function hideCover()     { cover.hidden = true; cover.innerHTML = ''; mask.classList.remove('cover-on'); }
```

**关键是把"卡片显隐"收敛成两个函数**，而不是散在五个地方各写一遍
`cover.hidden = false; cover.innerHTML = ...`。这一轮就是因为入口散着，
`startCard()` 里漏改了一个收尾的 `);`，直接把整个 `game.js` 变成 SyntaxError。

### 三、没有 node，怎么找 JS 语法错

改崩之后 `window.Game` 是 `undefined`，页面上所有游戏相关的东西一起消失。
这台机器上没有 node，没法 `node --check`。浏览器给的信息很有限
（`SyntaxError: missing ) after argument list`），但它至少把错误类型说清楚了。

于是写了 `tmp/jsscan.py`：逐字符扫一遍，跳过行注释 / 块注释 / 字符串，
维护 `(` `[` `{` 的栈，报第一个对不上的位置。**它不要钱地精确**：

```
!! 第 3282 行的 } 对不上第 3254 行的 (
```

顺着这两行一看就找到了（`showCover(` 开头，收尾还是 `'</div>';` 而不是 `'</div>');`）。

**它有已知误报**：正则字面量（`/\//g`）会被当成除号，之后整段就错位了 ——
`web/js/app.js:478` 的 `String(x.date).replace(/\//g, '-')` 就一直被报到不配平，
但那一行是对的。**所以它报错不一定是真错，但它说"配平"就一定是配平的。**

### 四、`resumeRound()` 不等于 `open()`

写探针量竖屏布局时，`.gg-guide` 量出来的 `scrollHeight` 和 `clientHeight` **都是 0**，
看起来像"新手入门卡片高度塌了"。其实是探针的锅：

- `open()` 负责把 `#game` 遮罩的 `hidden` 摘掉；
- `resumeRound(s)` 只负责把一局的字段灌回 `G` 并重建图表，**它假设面板已经亮了**。

探针绕过了 `open()` 直接调 `resumeRound()`，遮罩还挂着 `hidden`，所有元素 rect 都是 0。
补一句 `$('#game').hidden = false; await wait(60);` 之后，
`.gg-guide` 就正常报 `scrollHeight 1302 / clientHeight 673` 了。

**教训**：`display:none` 的祖先会让整棵子树的度量全变 0，而 `getComputedStyle().display`
读的是**指定值**、不会告诉你祖先藏着 —— 量布局之前先确认面板真的亮着。

### 附带：探针扫源码判断"文案改干净了没有"

想把"旧文案有没有残留"做成自动检查，第一版直接 fetch `/js/game.js` 然后正则搜关键词，
结果一直误报。两个原因：

- **注释里还留着旧文案**（我在 `resumeCard` 上方记了一句"上次那局还在 —— 问一句是接着玩还是重开"）。
  解法是先 `replace(/\/\*[\s\S]*?\*\//g, '')` 去掉块注释再扫。
- **搜的词太宽**。「天台」「久留美」是杠杆按钮的正常文案（`20× 天台` / `100× 久留美`），
  不是结算评语。应该只搜**被删掉的那几条整句**。

还有一个纯手误值得记：`P('… = ' + src.indexOf(k) >= 0)` —— 字符串拼接的优先级高于 `>=`，
它等价于 `('…' + idx) >= 0`，`NaN >= 0` 恒为 `false`。**五个检查项全部安静地显示 `false`**，
看起来像"全都没找到"。括号补上就好。

## 「当前所在地」那格为什么一直是灰的

用户看到的是一行灰 `--`，第一反应会去查"定位是不是没拿到"、"Open-Meteo 是不是挂了"。都不是。

它踩的是**同一类**坑的两个不同侧面：**数据是分两批到的，而界面只画了一次。**

### 一、谁画的，谁就得跟着数据重画

那一行只有一个渲染函数 `renderGeo()`，而它挂在**定位流程**上：开始定位画一次、成功画一次、失败画一次、
点行内的 ＋/✕ 各画一次。价格却来自另一条完全独立的链路 —— `warmQuotes()` 拉行情 → 写进 `S.quotes` / `S.briefs`。

两批数据到齐的时间不一样，而第二条链路结束时只重画了自选、热门、指数条，**没重画定位行**。
于是那一格永远停在"页面刚打开、行情还没有"的那一瞬间 —— 看起来像坏了，其实是**画早了就再没人管**。

修法只有一句 `renderGeo()`，但判断值得记：**看到一个"永远是空的数据格"时，先问它是谁画的、
那个函数挂在哪条事件上，以及数据真正到齐时会不会有人再叫它一次。**
"永远不刷新"比"取不到数"更常见，也更像 bug。

### 二、节流把「第一次」一起挡掉了

涨跌幅要昨收，昨收那一整段被 30 分钟节流包着（`if (Date.now() >= S.briefAt)`）。
开机时先跑过一轮轮询、把 `briefAt` 推到 30 分钟之后；而**定位城市和之后新加的自选城市是这时候才注册进来的**，
等下一次轮询时 `Date.now() < briefAt` → 整段跳过 → 这一轮一次都不取。表现就是"有价格、涨跌幅空着"。

**这里的错不在节流本身，在于"注册了新城市"这件事没有让节流失效。** 改法是给节流分两档：

- `due`（到点了）→ 照旧按 30 分钟批量刷全部；
- `!due`（没到点）→ 只补**一次都没成功过**的那些（`!S.briefs[i]`），失败过的给 1 分钟退避。

一句话概括：**节流只该挡"重复刷新"，不该挡"第一次获取"。**
任何"按 id 缓存 + 全局时间戳节流"的组合都要单独想一遍：新来的 id 在那段节流窗口里会不会被饿死。

### 三、别为了让格子好看而编数

定位出来的坐标**没有气象局站号**（`cma: ''`），昨收只能走 Open-Meteo。真取不到时那一格就让它空着 ——
编一个昨收出来，涨跌幅会变成一个假数，比灰色 `--` 更糟。


## 加「预警滚动条」时踩的坑

顶上那条会自己往左滚的预警提示条（行情软件里"滚动播报"那个位置）。功能本身不难，
难在两件事：**插进去一个元素把整页压塌了**，以及**怎么证明一行 CSS 动画真的在跑**。

### 一、`body` 是 grid，行数跟直接子元素一一对应

它长这样（`web/css/app.css:33`）：

```css
body{
  display:grid;grid-template-rows:46px 30px 34px minmax(0,1fr) 24px 22px;
  height:100vh;overflow:hidden;   /* 顶栏 / 天气条 / 指数条 / 主体 / 状态栏 / 免责声明 */
}
```

**六行，对六个直接子元素。** 我在天气条和指数条之间插了一个 `#warnTicker`，于是：

| 行 | 原定位 | 插入后实际拿到这行的元素 | 结果 |
| --- | --- | --- | --- |
| 3 | 指数条 34px | **滚动条** | 正常（它自己 26px） |
| 4 | 主体 `minmax(0,1fr)` | **指数条** | **被撑成 676px** |
| 5 | 状态栏 24px | **主体** | **只剩 24px** |

页面上看到的就是"顶栏、功能条、指数条都在，下面一片空"—— 主体其实没消失，是被挤成了一条 24px 的缝。

两个教训：

1. **`grid-template-rows` 里的裸尺寸是"按位置"分配的，不是"按元素"分配的。** 中间插一个子元素，
   后面所有元素整体挪一格。改布局前先数一遍"这套 grid 有几个直接子元素"。
2. 新插入的那一行要写 `auto` 而不是 `26px`。滚动条没数据时是 `[hidden]`（`display:none`），
   `auto` 会跟着塌成 0；写成固定值就会在"今天一条预警都没有"的时候留一道 26px 的空档。
   同理，`body.fullchart` 那份 `visibility:hidden` 名单也要把它加上，否则全屏看图时它还在上面挂着。

这个模板一共有三份，**改一份就要三份一起改**：`app.css:33`（桌面）、`:389`（窄屏竖屏）、`:479`（窄屏横屏）。
窄屏那两份比桌面多一个 `.mtabs`（四页签），所以行数是 8 和 7。

### 二、怎么证明一行 CSS 动画真的在跑

无头 Chrome 下有两个东西会让你误判：

- **`matchMedia('(prefers-reduced-motion: reduce)').matches` 恒为 `true`。**
  所以"减少动态效果就不滚"那条 `@media` 规则**在无头里永远生效** —— 读到
  `getComputedStyle(run).animationName === 'none'`、`duration === '0s'` 是**预期结果**，不是 bug。
  想验证 `@keyframes` 存不存在，可以临时给元素打一条内联 `animation`，能读到 `tickerRoll` 就说明它确实在样式表里。
- **`--virtual-time-budget` 下 `setTimeout` 瞬间触发，而动画时钟不走。** 所以"读两次 `transform` 看值变没变"
  完全证明不了任何事（实测前后都是 `matrix(1,0,0,1,0,0)`）。

可靠的判据是 **`element.getAnimations()`**：它走的是动画时间线本身，不受虚拟时间影响。
实测 `数量 = 1`、`playState = 'running'` 就说明动画确实挂在元素上并在跑（`currentTime = 0` 同样是虚拟时间所致）。

### 三、内容铺两遍 + `translateX(-50%)`

无缝滚动不需要 JS 逐帧改 `scrollLeft`：把条目渲染两遍，动画从 `0` 走到 `-50%`，
滚过一半的时候第二份的开头正好落在第一份开头的位置，接缝看不出来。要让它在内容不够宽时别做无效动画，
判据是 `run.scrollWidth / 2 > view.clientWidth`；时长按 `半宽 / 速度` 算（26 px/秒），
这样"内容多"表现为滚得久，而不是滚得更快。

还有一个容易忘的点：**刷新不能无脑重画 `innerHTML`**。每 15 分钟一轮的行情刷新如果每次都重设内容，
CSS 动画会被打回开头，看起来像一直在跳。用一个签名（`城市|本地/全国|条数|标题串`）挡住没变化的重画。

### 四、探针里不能用页面内部的 `$`

`$` 在 `app.js` / `wxui.js` 里是各自的**局部**变量，不是全局。探针脚本里写 `$('#warnTicker')`
会抛 `ReferenceError`，被当成 unhandledrejection 显示在页面状态条上（`⚠ Promise: $ is not defined`），
而且那个 `while` 循环会**立刻中断** —— 于是截图拍在开机中间，画面是错位的、看着像布局坏了。
排查了半天才发现是探针自己的错。**探针里一律用 `document.getElementById` / `document.querySelector`。**

## 开机时的两个异步任务，谁先到不一定

「当前所在地」那一格修完之后用户又发了一次同样的截图，于是找到**第三处**缺陷（前两处见上一节）。
复现的办法是把 `tjs.geo` 写进 localStorage **再 reload 一次**（让开机流程自己去读，
而不是在探针里手动调 `applyGeo`）—— 结果那一格是好的：

```
price="22.4" color=rgb(255,77,79) | pct="+0.31%" class=sw-pct p-up
```

说明**开机路径**没问题，用户八成看到的是浏览器缓存的旧 `app.js`
（GitHub Pages 给静态资源的 `Cache-Control` 是 10 分钟）。

但顺手发现 `applyGeo()` 里这条是错的：

```js
renderGeo(); renderWatchlist();
if (S.cur && S.cur.id !== LOC_ID) warmQuotes();   // ← 开机时 S.cur 很可能还没准备好
```

开机时 `initGeo()` 和 `selectCity()` 是**并行**的两个 Promise，定位比首次加载先回来完全正常。
这时候 `S.cur` 还是 `undefined`，整条 `if` 直接被跳过 —— 而报价的下一次机会是**默认 15 分钟**后的轮询。
表现就是那一格挂着灰 `--` 等一刻钟。改成：

```js
if (S.cur && S.cur.id !== LOC_ID) warmQuotes();
else if (S.geo) warmQuotes();
```

一句话：**"把数据准备好"和"界面准备好没有"是两件事，后者不该挡住前者。**
凡是 `if (某个异步任务的结果) { 做正事 }` 的写法，都要问一句：这个条件只是"顺路省一次请求"，
还是**错了就永远不做**？后者必须有个兜底分支。

## 行情头加日月、预警条搬家时踩的坑

### ① `body` 是 grid，行数和直接子元素一一对应

这一条这个项目里已经踩过两次了，两次的表现都是"某个区块莫名被撑大、主体剩一条缝"。

`web/css/app.css` 里 `body{display:grid;grid-template-rows:...}` 的每一行是**按位置**分给
`body` 的**第 N 个直接子元素**的，不是按类名。所以往这一层插一个新元素，后面所有元素整体后移一位：
顶上那个指数条会拿到"主体"那一行（`minmax(0,1fr)`），被撑到几百像素；主体自己只剩最后那 24px。

同一位子有三份模板要一起改：桌面（`app.css:33`）、`@media (max-width:860px)` 竖屏、
`@media (max-width:860px) and (orientation:landscape)`。另外 `body.fullchart` 还有一份
"全屏看图时把这些藏起来"的 `visibility` 名单，元素换爹之后选择器也得跟着换。

**教训**：往 `body` 下面加东西之前，先数一遍现在有几个直接子元素、模板里有几行。
数不上就别往这一层放 —— 这次把预警条挪进 `.quote-head` 之后，body 的行数就该还原，
于是三份模板同步减掉一行。

### ② `Weather.series()` 新增字段，忘了加进 `ALIGN_FIELDS` 会**静默消失**

副图的取数链是：`Weather.series()` 分桶聚合 → `alignSeries()` 按主图横轴对齐 → `optAir/optWind…` 画图。

中间那个 `alignSeries()` 只搬它名单里的字段。名单在 `web/js/wxui.js:46` 的 `ALIGN_FIELDS`。
往里加 `uv` 之前，紫外线数据一路都好好的（`hourly.uv` 有 2592 个数、`series()` 返回的
对象里也确实有 `uv`），但到了画图那一步就是没有 —— **不报错、也不是空数组，就是没有这个字段**。

这类"名单/白名单"式的静默丢弃，比抛异常难查十倍：每一层单独看都是对的。
所以 `ALIGN_FIELDS` 上面现在留了注释，写明"`series()` 里新增字段必须同步加到这里"。

### ③ 要滚的条子，内容不够长时**不能**铺两遍

无缝横向滚动的常规做法是把内容复制一份、`translateX(-50%)` 循环。
但如果内容本来就比可视区短，复制之后屏幕上是**同一条预警并排出现两次** —— 看起来像数据重复了。

正确顺序是：先只铺一遍 → 读 `run.scrollWidth` → **只有真的超过可视宽度**，才铺第二遍并挂动画。
先量后铺，多一次重排，换来"静态时不会重复"。

### ④ 月相没有任何数据源会给，得自己按朔望月算

Open-Meteo 给云量、紫外线、日照秒数，唯独不给月相（也不该给，那是天文不是天气）。
算法很简单：朔望月平均 29.530588853 天，拿一次已知新月当基准
（`Date.UTC(2000,0,6,18,14)`），相减后对周期取模、归一化成 0~1，
再八等分取名（新月/蛾眉月/上弦月/盈凸月/满月/亏凸月/下弦月/残月），
顺带把"照亮比例"按 `(1-cos(2πφ))/2` 算出来，显示成「满月 98%」。

精度足够 —— 朔望月的实际长度在 29.27~29.83 天之间浮动，本投影的误差是小时级，
而月相一天才走 1/29.5，看个大概完全够。

### ⑤ 风向别照英文缩写直译

`DIR16` 原来是 `['北','北北东','东北','东北东',…]` —— 这是把
`N / NNE / NE / ENE / …` 一个词一个字对译过来的，意思没错，中文预报里却没人这么说。
气象上通行的写法是 **北 / 北东北 / 东北 / 东东北 / 东 / 东东南 / 东南 / 南东南 /
南 / 南西南 / 西南 / 西西南 / 西 / 西西北 / 西北 / 北西北**。

用旧表拼出来是「北北东风」，用户看了一眼就来问"这是不是显示错了" ——
**一个"技术上正确但没人这么说"的字符串，在用户眼里就是一个 bug。**

### ⑥ 标签和数值抢空间时，让步的应该是数值

行情头那 21 个统计格是 `repeat(auto-fit, minmax(88px,1fr))`。
「风速」被显示成「风...」、「平均风速」显示成「平均...」—— 因为 `88px` 装不下
「平均风速」四个字加上「3.4 m/s」这样的数值，两边都是 `text-overflow:ellipsis`，谁先被挤谁先断。

修法是两条一起：列宽下限提到 `108px`，并且**给标签那一侧 `flex:0 0 auto` + `overflow:visible`**
（标签永不收缩），把"挤"这件事全推给数值侧。

判断标准很简单：**标签是"这个数是什么"，数值是"这个数是多少"。标签被截了，这一格就等于没有。**
反过来数值被截还有 `title` 悬停兜着，而且大多数情况下数值本来就短。

## 统计格「同类放一起」：为什么不能只调数组顺序

有人看完行情头说：「行情头里同类型的数据是不是放一起更好啊」。

第一直觉是**把 `items` 数组重新排一遍**就行。但排完发现没用 —— 因为那时 `.qh-stats` 是

```css
display:grid;grid-template-columns:repeat(auto-fit,minmax(108px,1fr));
```

**`auto-fit` 是按行填的，一行的容量由容器宽度决定（那时是 4 格）**。这意味着
"相邻"这件事是**按 4 个一组**成立的：你想要的组只有正好 4 个、而且正好落在第 1、5、9… 位，
它才会在同一行上。当时有 21 格，`21 % 4 = 1`，无论怎么排，最后总有一格落单；
而且**任何不是 4 的倍数的组，都会把下一组的第一格吸到自己那一行的行尾**。

于是走了两步：

1. **让格数变成 4 的倍数。** 21 → 20：把「降水量」「降水时数」合成一格
   （`0.0 mm / 0 h`）。这两格本来就是同一件事的两面，合起来不丢信息，
   而且正好凑成 5 组 × 4 格，每行对齐。
   *（另一条路是再加三个指标凑 24，但那属于擅自扩功能。）*
2. **每组包一层自己的小栅格**，而不是在大栅格里靠顺序凑：

```css
.qh-stats{display:flex;flex-direction:column}
.qg{display:grid;grid-template-columns:repeat(auto-fit,minmax(108px,1fr));gap:2px 10px}
.qg + .qg{margin-top:4px;border-top:1px solid #2a313d}
```

这一步才是关键。**纯顺序方案只在"桌面 4 列"成立**；窄屏时 `.qh-stats` 会变成 3 列，
4 格一组的第 4 格就会被顶到下一行，而那一行剩下的位置是**下一组**的 —— 组又散了。
每组各自是个栅格之后，**组内永远连在一起，组与组之间永远断开**，跟容器分几列无关。

实测（`tmp/qhgrid.js`）：桌面 1582px → 5 组各占一行 4 列；窄屏 500 CSS px → 5 组各排成 `3+1`，
仍然各自成块。两种情况下**被截掉的格子都是 0**。

### 顺带修掉的两件事

- **每格的下划线去掉了。** `.qs` 原来每格都有 `border-bottom:1px dashed #1f242e`，
  分组之后一行就是一组，**每格一条虚线 + 组间一条实线**叠在一起显得很乱。
  现在只保留组间那条实线。
- **反而更省高度。** 21 格摊 6 行 → 20 格排 5 行，行情头从 157px 降到 **141px**，
  主图那块多出 60 多像素。**"整理信息"不一定是加东西，这次是净赚。**

## 「记住上次的设置」：为什么不能只存在存档里

**需求原话**：「模拟游戏能否记录上次游玩时的设置」。

### 症状为什么只出现在「行情速度」上

面板上有六项：本金 / K 线周期 / 行情速度 / 杠杆 / 仓位 / 音效。改之前：

| 设置 | 存法 | 表现 |
| --- | --- | --- |
| 本金 | `wxgame_cash`，`setCash()` 每次都写 | 记得住 |
| K 线周期 | `wxgame_bar`，`setBar()` 每次都写 | 记得住 |
| 行情速度 / 杠杆 / 仓位 / 音效 | **只写进 `saveRound()` 的存档里** | 有存档才记得住 |

于是「行情速度」成了最扎眼的那一个：它**只有在你把这一局存下来的时候**才被顺带记住。
新用户、刚点过「结束本局」、玩完一局结算过 —— 这三种情况下 `wxgame_save` 是空的，
面板就只剩本金和周期还在，**速度被打回默认的「悠闲」**。

### 根因：把两类东西存在了同一个地方

`saveRound()` 里捎带 `barIdx / speedIdx / lev / pct / sound` 本身没错 ——
「接着玩那一局」的时候，确实应该把当时的档位一起还回来。错的是**把"设置"的下落
绑在了"局还在不在"上**：

    wxgame_save  = 局      → 点「结束本局」该清，清了是对的
    （没有别的了）          → 于是设置跟着一起没了

**该分开的东西必须分开存。** 现在多一份 `wxgame_cfg`：

    开局：    cfg 当默认值  → 填进 G
    有存档：  存档里那套覆盖 G，并且顺手写回 cfg（那就是"目前正在用的"）
    结束时：  清 save，不动 cfg

`resumeRound()` 里那句 `saveCfg()` 是这条链的收口：**恢复存档之后立刻把设置刷成存档里那套**，
这样这局结束之后再开局，还是你最后用的那一套。

### 存档键带命名空间

`web/js/util.js` 里的 `storeGet/storeSet` 包了一层前缀 `NS = 'tjs.'`，
所以 `storeGet('wxgame_cfg')` 在 DevTools 里看到的是 `localStorage['tjs.wxgame_cfg']`。
写探针时如果用 `localStorage.getItem('wxgame_cfg')` 去读，**永远读到 null**，
而页面自己读写得好好的 —— 看起来就像"保存失败了"。第一版探针就栽在这上面：
它读到 null，又把结论写进没前缀的键，导致后面几条断言全部误判。

### 别把"点不亮的按钮"记下来

`lev` 和 `pct` 的合法值是**从 DOM 里现查**的，不是写死的常量表：

    function pickSeg(sel, attr, val, d) {
      const vals = U.$$(sel).map(b => +b.dataset[attr]);
      return vals.indexOf(+val) >= 0 ? +val : (vals.indexOf(d) >= 0 ? d : (vals.length ? vals[0] : d));
    }

理由是以后加减档位（比如再加一个 200×）时，旧设备上记着的那个值在新版本里可能不存在 ——
写死常量表的话就会得到一个**谁也没高亮的面板**：值在 `G` 里是真的，按钮上却什么都没选中。
现查 DOM 则天然对齐。

同理 `barIdx` 用 `clampIdx(v, BAR_MIN.length, 2)` 卡范围，`cash0` 卡在 `CASH_MIN ~ CASH_MAX`。

### 老版本迁移

`wxgame_bar` / `wxgame_cash` 是上一版分开存的键。`loadCfg()` 在**读不到 `wxgame_cfg` 时**
回落到这两个键：

    const rawBar = c ? c.barIdx : storeGet('wxgame_bar', null);
    const rawCash = c ? c.cash0 : storeGet('wxgame_cash', null);

`v` 对不上的旧格式 cfg 一样当作"没有"，走同一条回落路径 —— 这样升级上来的人
不会突然丢掉已经用熟的周期和本金。写这两个键的代码暂时留着（`setCash` / `setBar` 里那两行），
不为别的，只为**万一有人还开着旧版本的缓存页面**，那边读的还是老键。

### 怎么验「记住」

关键是**必须真的整页重载**，不能在同一段 JS 里关掉面板再打开 ——
后者只证明"内存里的 G 没被重置"，跟 localStorage 一点关系都没有。
`tmp/cfg.js` 的做法：第一趟调设置并写一个 `tjs.__cfg_phase = 'B'` 标志，然后 `location.reload()`；
第二趟（脚本重新执行、`G` 全新构造）读标志、只跑 B 段。

顺带一个坑：**`location.reload()` 会把探针的 `<pre id="o">` 一起冲掉**，
第一趟的结论就没了。所以 A 段结束时把 `O.textContent` 拆行写进 `localStorage`，
B 段开头再打出来 —— 不然只能看到后半截，前半截的失败会被误当成通过。

## 竖屏里 `flex:1 0 100%` 的意思会翻个面

预警条（`#warnTicker`）在桌面上是横在行情头底部的一小条。搬到竖屏之后，它变成了一根
从屏幕中部通到下部的大红竖条，宽约 172px、高约 700px，标签「⚠ 本地预警」竖着排在里头。

桌面那条规则是好用的：

```css
.quote-head            { display:flex; flex-wrap:wrap; }
.quote-head > .ticker  { flex:1 0 100%; order:9; }   /* 占满一整行宽度，排到最后 */
```

而竖屏块里有一句

```css
.quote-head { flex-direction:column; }
```

**`flex-basis` 是沿主轴量的。** 主轴从横向变成纵向之后，同一个 `100%` 就从"整行宽度"
变成了"整个高度"：`flex-grow:1` 把它撑满剩余高度，`align-items:flex-start` 又把宽度
收成内容宽 —— 一条 172×700 的红柱子就这么来的。

**教训：凡是写了 `flex-basis`（尤其是百分比）或者 `flex:1` 的元素，一旦祖先可能会
`flex-direction:column`，就必须在两个方向上都写清楚。** 竖屏里重写一条就行：

```css
@media (max-width:860px) {
  .quote-head > .ticker { flex:0 0 auto; width:100%; margin-top:5px; }
}
```

`flex:0 0 auto` + 显式 `width:100%` —— 不伸不缩、宽度自己说了算，不再问主轴要长度。

## 按元素名写的省略号规则，会盖掉按内容写的

更早那轮修过「风...」：统计格里的**标签**被挤到省略号，用户以为自己看错了。
当时的修法是让标签永不截断、挤的时候收窄数值侧：

```css
.qs b    { flex:0 0 auto; overflow:visible; text-overflow:clip; }
.qs span { min-width:0; overflow:hidden; text-overflow:ellipsis; }
```

竖屏块里后来又加了一句：

```css
.qs b, .qs span { overflow:hidden; text-overflow:ellipsis; }
```

**选择器权重一样，但竖屏块在后面、而且直接把 `.qs b` 又指回了 `hidden`** —— 标签截断
就这么被装回来了，而且只在竖屏出现，桌面上测一切正常。

两个教训叠在一起：

1. 同一套元素在媒体查询里"重写一遍"时，最容易漏掉的不是新增的规则，而是**把父级
   刚调好的东西又覆盖回去**。改竖屏之前，先搜一遍同一个选择器在桌面块里长什么样。
2. 别用 `a, b { ... }` 这种"顺手把两个都写上"的写法去覆盖两个**需求相反**的元素。
   标签要 `visible`、数值要 `hidden`，本来就不该共用一条规则。

## 真机宽度在 Windows 上量不到 —— 用 iframe 造一个

无头 Chrome 的窗口宽度会被夹到大约 **500 CSS px**（`--window-size=390,844` 拿到的是 500×692，
`--force-device-scale-factor=2` 也不会把 CSS 视口除半）。而这一轮的 bug 只在 407px 上下出现。

**办法是把页面装进一个定宽 iframe：**

```js
var f = document.createElement('iframe');
f.style.cssText = 'position:absolute;left:0;top:0;width:407px;height:760px;border:0';
f.src = '/index.html';
document.body.appendChild(f);
```

iframe 有**自己的视口**，里面所有媒体查询都按 407×760 算 —— 和被塞进真机是一回事，
`getBoundingClientRect()` 量的也是真实布局值。（探针和页面同源，所以父页可以往
`localStorage` 里播 `tjs.geo` 的种、也可以直接 `f.contentDocument.getElementById(...)`。）

截图同理：把 iframe 摆在一个更大的窗口里（比如 500×900）拍下来，再按 `(0,0,407,760)`
裁一刀 —— **比强行让 Chrome 缩窗口靠谱**，因为窗口尺寸是它说了算，不是我们。

## 一个容器放不下时，先问它是"该折"还是"该滚"

竖屏的行情头有五组统计格。407px 宽时每组四格要排成 3+1 两行，五组就是 180px ——
主图本来就只有 230px 上下。

这里有一个**已经在别处做过的选择**可以照抄：`.pane-center` 在竖屏本来就带
`overflow-y:auto`（"实在放不下时改由它内部滚动"）。但行情头**不适合滚**：它是"一眼扫过去"
的读数区，滚起来等于看不见。

所以这一块选了**折叠**：默认只留两组，其余折起来，点一下全放。
两条判断标准，记在这儿备查：

- **要"一眼扫完"的读数区 → 折叠**（行情头统计格、K 线周期选择）：宁可少显示，也要能一眼看全；
- **要"逐条看"的列表 → 滚动**（逐时成水流、自选列表）：条目本身就是一条一条读的。

还有一个细节：折叠的默认值只在窄屏生效（宽屏永远全放），并且**用户点过之后就按他点的来**
（存 `tjs.qmore`，`null` 才算"没表过态"）。否则在手机上点开一次，回桌面还是收着的，很怪。

## "本地"是个会过期的词

预警滚动条第一版用的是**定位所在**的区市：拿 `S.geo.district / S.geo.city` 去标题里找。
这在"我就看自己家"的时候完全正确，可你一旦在自选里切到北京看行情，条子还停在广州 ——
它明明长在**北京那块行情头的底下**，滚的却是广州的预警。这不是筛选逻辑错，是
**"本地"这个词的含义变了**：条子挂在谁头上，就该说谁的事。

改成 `S.cur`（当前正在看的那个城市）之后，"本地"才名副其实。代价是原来的
`geo ? '本地' : cur.name` 那套标签逻辑也要跟着扔 —— 现在**永远写地名**（「⚠ 广州预警」），
因为"本地"两个字在切到别的城市之后就是骗人的。

**一条通用规则：凡是给用户看的"这里 / 本地 / 当前"，先问一句"这里的参照物是什么"。
如果参照物是可能变化的状态（定位、选中项、URL 参数），要么让它跟着变，要么就别用这种词。**

## 区一级的预警，标题上写的往往是市

定位到「天河区」时，如果只拿"天河区"去标题里筛，多半一条都筛不到 —— 因为气象局的标题写的是
「广东省广州市发布森林火险黄色预警信号」。区一级往往不单独发预警。

所以键是**一组**：

- 正在看地级市（`cities.json` 里那座）→ 只拿市名（「广州」）；
- 正在看区县（搜索出来的 `lev === 3`，或定位到的 `loc === true`）→ 市名 + 上级市名。

```js
keys.push(cur.name);
if ((cur.loc || cur.lev === 3) && cur.city && cur.city !== cur.name) keys.push(cur.city);
```

**地级市自己不能带上上级** —— 那会把「吉林市」和「吉林省」混在一起，一次卷进全省的预警。
所以判据不能写成"只要有 `city` 字段就带上"，得写清"只有区一级才带上"。

（`cities.json` 的地级市记录本来就没有 `city` 字段，`places.json` 的区县记录才有 ——
但别依赖这个巧合，显式判 `lev / loc` 更经得起以后改结构。）

## 排序也要跟着参照物换

原来的排序是说"点名了定位那个区的那条排前面"。改成跟着当前城市之后，这个"区"只有在
**正在看区一级**的时候才存在，看地级市时所有命中项的名字里都含市名，排序应该是恒等的：

```js
const deep = (cur && (cur.loc || cur.lev === 3)) ? cur.name : '';
const spec = w => (deep && (w.title || '').indexOf(deep) >= 0) ? 0 : 1;
```

写 `spec` 的时候容易忘的是**"这个优先级只在某些情况下存在"** —— 如果直接拿 `cur.name` 去比，
看地级市时所有条目都命中，`spec` 恒为 0，虽然结果一样，但读代码的人会以为这里在做有意义的事。

## 怎么验"条子跟着城市走"

探针 `tmp/tk2.js` 的关键设计：**把定位故意设成和当前城市不一样**，然后一路 `selectCity()`。

- 定位种子写广州天河区（`tjs.geo`），但清掉 `tjs.lastCity` 让开机落在别的城市；
- 依次切 广州 → 北京 → 定位城市（`__APP.LOC_ID` = `__loc__`）→ 广州，
  每次等 `S.cur.id === 目标` 再等 4.5 秒（`tickerRefresh` 那一趟网络回来），再读 `#warnTicker.hidden`。

**最关键的一格是"切到北京"**：定位是广州，所以改之前条子一定会继续显示广州那条；
改之后必须是 `hidden = true`。**如果只测"切到广州有广州的预警"，改不改都能通过** ——
测试用例必须落在"改之前会失败"的那个点上。

（另外注意 `#tickerTag` 在 `hidden = true` 之后仍留着上一次的文本，这是正常的：
读它之前先看 `hidden`，别把隐藏元素的残留文本当成结论。）

## 结算卡的「收场白」：加一句话也要先划清楚它管哪几档

结局收场白（爆仓一句红的、好结局一句金的）这件事本身没什么技术含量，坑全在"**加在哪儿、
加给谁**"上。记四件事：

### 一、先说清"这一句是干什么用的"，再决定它出现在哪几档

结算卡上原本已经有一句 **评语**（`verdict`），所以新加的这句必须先回答"那它和评语有什么
不一样"，否则就是往同一张卡上堆两句意思接近的话。这里的切分是：

- **评语**回答"**这一局发生了什么**"（"方向错了就认。好在仓位没要你的命 —— 活着就有下一局。"）；
- **收场白**回答"**就这样收场了**"（"最后请欣赏绚丽多彩的空中飞人表演！"）。

切分清楚之后，"加在哪几档"就自己出来了：只有**两个明确的结局**配得上收场白 ——
爆仓，和冲到 B 档以上。C / D / E（小赚、持平、小亏）那些结果本来就不痛不痒，
再加一句反而把"这次到底算好还是不好"搅浑了。**中间态不是"暂时没想好台词"，是"这里就不该
有台词"** —— 不做这个决定，最后必然变成每张卡都挂一句，等于没有。

### 二、边界要拿数字钉死，不要拿感觉

"好结局"是个感觉词。落到代码上必须是一条能一眼看懂的判断：

```js
const good = !liq && (gr === 'S' || gr === 'A' || gr === 'B');
```

它是按**已经算好的档位**判断的，不是再算一遍收益倍数 —— 档位表（SSS/S/A/B/C/D/E/F）
是这张卡唯一的"官方口径"，收场白跟着它走就不会出现"卡片顶上写着 B，底下却按 ret 算成 C"
这种两套标准的裂缝。

边界值必须实测，不是推的：**ret = 1.50 正好是 B**（有收场白）、**ret = 1.20 是 C**（没有）。
这两个用例是分开跑的，不是"顺便看看"。

### 三、位置用 DOM 关系断言，不要用"看起来在下面"

探针不该只读 `textContent`，还要读结构：

```js
beforeBtns:   !!(f && btns && (f.compareDocumentPosition(btns) & Node.DOCUMENT_POSITION_FOLLOWING)),
afterVerdict: !!(f && dim  && (dim.compareDocumentPosition(f)  & Node.DOCUMENT_POSITION_FOLLOWING)),
```

`compareDocumentPosition` 是 DOM 自己给的答案，比我肉眼对着截图数行数可靠。
这一轮**没截图也能确认顺序**；截图只用来做观感和颜色（`getComputedStyle(f).color`
拿到 `rgb(255,143,145)` / `rgb(255,214,102)`，和设计稿对得上）。

### 四、怎么在探针里"制造"一个指定的结局

结算卡的输入是 `G` 里的几个字段，而 `global.Game = { open, close, G, ... }` 把 `G`
**整个暴露出来了**（`weather-exchange/web/js/game.js:3528`），所以不用真打一局：

```js
G.pos = 0; G.avg = 0;                         // 先平掉持仓，equity() 就等于现金
G.cash = G.cash0 * 2.0;                       // 现金 = 本金 2 倍 → ret = 2 → A 档
t.endRound('timeup');                         // 走正常的结算路径，不是伪造卡片
G.cash = 0; t.endRound('liquidated');         // 爆仓
```

要点是**走 `endRound()` 本身**，而不是自己拼一张卡片 —— 测的是"真实路径上会不会出现这句话"。
每次重测之前重新 `open()` 一次，让 `G.cash0` 等字段回到正常状态，否则上一轮的 `G.cash`
会带进下一轮。

另外顺手给 `weather-exchange/tmp/bk.js` 加了个 `?cash=2.6` 参数（结算截图专用），
原因很实际：**结局收场白只在 B 档以上出现，不指定倍数的话随手一拍多半拍到"没有那句"的版本**，
文档截图看起来就像功能没做。**文档截图要拍的是"这个功能长什么样"，不是"随便跑一局长什么样"。**
